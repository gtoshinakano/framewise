# External integration guide

Framewise is a local-first video analysis service. The OpenAPI document is at `/openapi.json`, interactive Swagger UI at `/docs`, and this guide as Markdown at `/api/integration-guide`. Resolve all paths in this guide against the Framewise server origin, for example `http://192.168.0.6:8080`. The listening address may differ on your installation. No authentication is required on this trusted network. Treat the server as the source of truth; do not guess IDs or assume a title is unique.

## Data relationships and units

A **project** contains **episodes**; each episode has one preserved original video. Preparation extracts metadata, a proxy, audio if present, and frames. The user triggers hard-cut detection, which creates **cuts** on the episode timeline. A cut has a UUID, `episode_id`, zero-based `cut_index`, `start_time`, and `end_time`: `CUT1` conventionally means the active cut with `cut_index` 0, not index 1. IDs are UUID strings, titles are labels, timestamps and durations are seconds from episode start, and a cut covers `[start_time, end_time)`. Cuts can be edited, archived, reactivated, reordered or merged: keep the cut UUID and refresh its current metadata before use. Archived cuts have `active=false` and negative indices; they are not in the current timeline. A cut may cross a **chunk** boundary; chunks are independent working segments, not visual cuts.

A cut has editable notes, an `analysis_enabled` flag for future queued visual analysis, and zero or more **analysis results**, each with a `kind`, title, content, origin and optional model, job, prompt, settings and input context provenance. Disabling a cut does not change already queued snapshots or existing results. Analysis is not automatically available for every cut. Results are revision chains: `parent_id` points back and `superseded_by` points forward. Origins include `model`, `manual`, `manual_edit`, and `assistant_edit` (a Cut Assistance proposal the user applied; `settings.assistant_edit` records the chat model and proposal). Default result reads return current revisions; `history=true` returns all revisions. Cut detail exposes the current summary and frame analysis content without result metadata. All current results are usable in analysis and summary regeneration. Use origin and provenance and review content where accuracy matters. `cut.results` is a separate legacy editable field, not the revisioned results list. `context` and `settings` contain model-specific JSON and may be empty; preserve unknown keys.

For clients explicitly authorized to edit results, `POST /api/cuts/{cut_id}/analysis-results` creates a result and `PUT /api/analysis-results/{result_id}` appends a human revision. Results have no approval status. Editing an already superseded revision returns 409. Deleting an individual current revision restores its parent as current when one exists.

For clients authorized to cancel work, `POST /api/jobs/{job_id}/cancel` cancels a queued GPU job (visual analysis, character detection, text steps, sequence steps, subtitles, transcription, voice samples) or a running one that can stop at its next checkpoint; media preparation, cut detection and exports cannot be cancelled. A cancelled job has the status `cancelled` (jobs cancelled before 2026-11-15 were stored as `failed` with the stage `Cancelled` and have been converted); it is never a failure. A running job keeps working until its next checkpoint and writes nothing after it; its results so far stay. Running text cancellation frees the local worker; a remote provider may continue processing an already submitted request. `GET /api/episodes/{episode_id}/queue` lists what runs, waits and failed in one episode, and `GET /api/episodes/{episode_id}/runs` pages through its finished runs.

The episode brief endpoint returns each cut’s current `production_brief` (Cut summary Markdown, result ID, origin, model, job and creation time), or null when unavailable. Existing summaries remain available and may predate the production brief format. Cut and transcript source timestamps are episode-relative; the generated brief requests clip-relative timing. The export snapshots the same brief. Saved human answers and corrections are included in future queued generations; each job retains its own request snapshot. The model receives text evidence, not original audio.


**Context items** are project-wide when `episode_id` is null, otherwise episode-specific. Items include character, world, scenario, object, chapter, and general notes. **Transcript segments** have episode-relative time ranges, text, a deletion marker, and optionally `character_context_id`, linking to a character context item. Default episode transcript reads and cut detail include current non-deleted segments; segments can extend outside the cut. `history=true` on transcript returns all revisions including deleted. Segment `origin` is `model` (transcription), `manual`/`manual_edit` (the Audio editor) or `assistant_edit` (a Cut Assistance proposal the user applied; a reworded line replaces its word-level fragments with one segment and the fragments end as deletion revisions). A **voice sample** links to a character through `character_context_id`; it can come from uploaded audio or one or more episode ranges. `preview_available` indicates whether its reference audio is currently available. Match IDs, not names. Its WAV reference is not necessarily a transcript of the cut.

## Recommended read sequence

1. Check `GET /api/health`. List `GET /api/v1/projects`, select the project by ID, then `GET /api/v1/projects/{project_id}/episodes` and select an episode by ID. Duplicate names are possible. Read `GET /api/v1/episodes/{episode_id}` for duration, dimensions, status, and `has_audio` (null before probing). Preparation or detection may still be running or failed. Check `GET /api/episodes/{episode_id}/status` for current job state.
2. List `GET /api/v1/episodes/{episode_id}/cuts?offset=0&limit=100`; follow `next_offset` until null. Active cuts only are returned by default. Use `include_archived=true` to include archived cuts after active ones. For CUT1 select the active item with `cut_index=0`. Pagination reflects live data and can shift if cuts are edited while paging; repeat the read if a consistent snapshot matters.
3. Call `GET /api/v1/cuts/{cut_id}`. It includes project identity, the cut, applicable context, overlapping transcript, burned-in `subtitles` (see below) and adjacent cut metadata. `cut_summary` is the current Cut summary text; `first_frame` is the current structured first-frame analysis (the opening still) and `motion` is the cut's motion direction (see Visual results below): since 2026-11-18 it is derived from the keyframe analysis (`motion_source: "keyframe_analysis"`), for cuts analysed earlier from their video analysis (`motion_source: "video_analysis"`). `keyframes` is the keyframe analysis as prompts read it (each keyframe's states, then what changed between consecutive keyframes) and `performance_beats` the current beats (null when not written yet or written from an older keyframe analysis). `last_frame` is only filled for cuts analyzed before last-frame analysis was removed and is superseded by `motion` when both exist. Each is null when unavailable. Empty arrays mean no matching data is currently available, not that analysis succeeded. The response is a convenience aggregation rather than a transactionally consistent snapshot: refresh when editing is concurrent.
4. For full result revision history call `GET /api/cuts/{cut_id}/analysis-results?history=true`; the default is current revisions. Set `include_context=false` to omit potentially large captured evidence. For full transcript use `GET /api/episodes/{episode_id}/transcript` (or `?history=true`). `GET /api/cuts/{cut_id}/analysis-context` also supplies current results from neighboring cuts. `GET /api/projects/{project_id}/context` returns all project and episode-scoped context items; filter `episode_id` yourself when needed. `GET /api/cuts/{cut_id}/analysis-config` shows the current analysis settings. Job IDs in results or the episode's jobs list can be passed to `GET /api/v1/jobs/{job_id}` to inspect the queued input snapshot and any retained intermediate cut evidence. Snapshots can be large, can represent older data, and do not imply a job succeeded.
5. To fetch a character's reference, list `GET /api/projects/{project_id}/voice-samples`, find a matching `character_context_id`, check `preview_available`, then download `GET /api/voice-samples/{sample_id}/audio`. `GET /api/v1/voice-samples/{sample_id}` also returns metadata and the stored model-specific voice embedding. Do not assume every character has a sample. To obtain cut audio, use `GET /api/v1/cuts/{cut_id}/audio?before=1&after=3`. This returns prepared mono 16 kHz PCM WAV from the original's first audio stream, with up to one second before and three seconds after the cut. Each margin is non-negative and at most 3600 seconds. The excerpt is clipped to the episode and available audio; `X-Audio-Start-Seconds` and `X-Audio-End-Seconds` are the actual sample-aligned episode timestamps. Archived cuts can also be requested. No audio, not-yet-prepared audio, or unavailable files return 404; an excerpt with no samples or invalid prepared audio returns 409; an excerpt exceeding WAV size limits returns 413. Do not assume silent video has an audio file.

   Optionally pass `min_duration=2` to request at least two seconds in the WAV (maximum 3600 seconds). A short excerpt extends into available audio after it, then before it, and is padded with silence at the end if the source is still too short. The timestamp headers describe source audio only, excluding padding. The cut results download button uses this option.
6. For a cut's default image, download `GET /api/cuts/{cut_id}/frame/first`. The brief's `suggested_frame_url` points to this first frame when the original, proxy, or a saved first-frame thumbnail is available; it is not a model recommendation. The boundary endpoint can recreate a JPEG from the video, and temporary extraction failures return 503. Use `/last` for the other boundary or `GET /api/analysis-results/{result_id}/frame` to inspect a particular analyzed frame. Original video, proxy, or prepared whole-episode audio can be fetched through `GET /api/episodes/{episode_id}/media/original`, `/proxy`, or `/audio`. `GET /api/episodes/{episode_id}/frames` lists interval frames, and `/waveform` returns waveform data. The existing `GET /api/episodes/{episode_id}` also returns all active and archived cuts, chunks, job metadata, and preparation settings; it can be large.

## Example

```sh
BASE=http://192.168.0.6:8080
curl "$BASE/api/v1/projects"
curl "$BASE/api/v1/projects/PROJECT_UUID/episodes"
curl "$BASE/api/v1/episodes/EPISODE_UUID/cuts?limit=100"
curl "$BASE/api/v1/cuts/CUT_UUID"
curl "$BASE/api/cuts/CUT_UUID/analysis-results?history=true"
curl -o first-frame.jpg "$BASE/api/cuts/CUT_UUID/frame/first"
curl -OJ "$BASE/api/v1/cuts/CUT_UUID/audio?before=1&after=3"
curl -o voice.wav "$BASE/api/voice-samples/VOICE_SAMPLE_UUID/audio"
```

Replace placeholders with returned IDs. Quote URLs containing `&`. JSON errors use `detail`; HTTP 404 means the requested object or media is absent, 409 indicates a state conflict, and 422 indicates invalid parameters. Available data and URLs can change after edits, deletion, or reruns. Media downloads can be large. Polling and caching clients should retry according to their own needs and respect failed job states. The `/api/v1` integration endpoints are read-only; the existing `/api` also contains mutating endpoints. Do not invoke mutations unless explicitly requested.

## Agent-ready briefs and downloads

`GET /api/cuts/{cut_id}/structured-analysis` returns structured single-cut outputs as JSON objects, including their type, source and revision links. Pass `?history=true` for all revisions. The brief's `initial_frame` includes the current structured initial-frame result when available. A missing result means it has not yet been generated; do not infer one from a legacy summary. Editing an existing structured result through `PUT /api/analysis-results/{id}` requires `content` to be a JSON object encoded as a string, and creates a new revision.

Single-cut runs produce two structured results, `initial_frame` and `keyframe_analysis`, and the keyframe result queues a text job that writes a third, `performance_beats`; see Visual results below for their fields. Cuts analysed before 2026-11-18 have a `video_analysis` instead of the last two; it stays readable and is still used for them, and the video stage can no longer be queued (`POST /api/cuts/{cut_id}/analysis-stages/run` with `video_analysis` answers 410). Queuing a visual run also queues the cut's keyframe selection when it has none (`payload.wait_for_keyframes`); the run waits for it. The last frame is no longer analyzed: `last_frame` results exist only on cuts analyzed earlier, stay readable through the same endpoints and in revision history, and are not updated by new runs. Subtitles are no longer a per-cut result: older cuts may still carry a historical `subtitle_ocr` result, but new subtitle evidence comes from the episode-wide track described under Subtitles. New visual-only runs do not automatically queue text processing. `POST /api/episodes/{episode_id}/visual-analysis` queues individual visual jobs for enabled cuts; the older `/api/episodes/{episode_id}/analyze` route is a visual-only alias and returns all `job_ids` plus the first `job_id` (or null if nothing was queued). Batch queueing skips cuts with queued or running visual jobs; a single-cut request for an already queued cut returns 409. Queue a separate `consistency_summary` with `POST /api/cuts/{cut_id}/consistency-summary`, or queue consistency and dependent briefs for ready enabled cuts with `POST /api/episodes/{episode_id}/text-processing`. Jobs queued under the earlier workflow retain their original automatic behavior. Its visual and transcript inputs are captured at queue time (the episode context and the pictures when the job starts); the result contains source IDs and a snapshot of the evidence. Its separate job can fail even when visual analysis succeeded. A newer summary revision blocks an older queued job from overwriting it. `GET /api/cuts/{cut_id}/analysis-stages` lists stage attempts, errors, and elapsed seconds; interrupted attempt times use the last worker heartbeat. Read stage state and job status before assuming a run completed. A frame result has `composition`, `setting`, `lighting`, `camera`, `visible_characters` (one entry per character the user marked: `character`, `character_context_id`, `appearance`, `position`, `pose`, `expression`, `action`), `background_people` (unmarked people, one line) and `notes`; older results carry `other_visual_details` and `uncertainties` instead. A last frame with `mode: "changes"` lists only differences from the first frame (`unchanged` means the first frame still holds; `new_in_frame` per character, plus `left_frame` and `based_on_initial_frame` describe who came and went and what it was compared with); read it together with the first frame, or use the composition view, which already merges the two.

### Visual results

The results follow the way a cut is reproduced: a still image of the first frame, the dialogue audio, then a video that animates the still. The first frame decides how a cut starts, the keyframes decide what changes afterwards, and the performance beats turn both into a timed acting plan.

`keyframe_analysis` (`contract: "keyframes-v1"`) describes the frames the keyframe selector picked where the picture changes (labelled `F1`… with `t`, seconds from the first frame, and the source frame `ordinal`). `method` is `hybrid` (Qwen3.5-27B on the frames plus DWPose body keypoints) or `qwen` (Qwen3.5 alone, when the keypoint model is not installed). `roster` lists the named characters it was told (`source` `target_slots` when the names came from the Target frames tab, else `first_frame`). `frames[].characters` gives each visible character's `state` at that keyframe (the vision model) and `pose` (the state measured from keypoints, when read). `segments` has one entry per pair of consecutive keyframes with `start`/`end`, `camera` (`move`: static, pan_left/right, tilt_up/down, zoom_in/out, dolly_in/out, truck, orbit, shake or unclear, always measured from the background pixels with people masked out, never a model's guess), per character `walking`, `speaking`, `blinking` (yes/no/unclear) and `changes` (`part`: body_pose, head, eyes, mouth, arms, hands, legs, position, expression; `description`; `source`: `dwpose` when measured from keypoints, `qwen` when read from the images), and `other_changes` (outfit, color, lighting, object, background, effect). A change happened somewhere between its two keyframes; nothing between them was seen. `cut` holds the episode times the analysis was made for.

`performance_beats` (`contract: "beats-v1"`) is written by a text model from the first frame, the keyframe analysis and the transcript timing (never the words): `beats` tile the cut, each with `start`, `end`, `camera`, `intent` (what the beat does dramatically) and per visible character `body`, `face`, `gaze` and `mouth` (`speaking`, `closed`, `open`, `not_visible`, `unclear`), plus the `speech` lines inside it. `speech` lists every transcript line in the cut once with `line`, `speaker`, clip-relative `start`/`end`, `delivery` (`on_screen` lip-synced, `off_screen`, `inner_voice`: visible with the mouth still, `narrative`: a voice over the picture) and the app's `suggested` delivery. `based_on.keyframe_analysis` names the keyframe result it was built from; beats whose keyframe result was replaced are stale and not used. `checks` lists what the app noticed (a mouth speaking with no line, a lip-synced line whose speaker was not seen).

`initial_frame` describes the opening still: `composition`, `setting`, `lighting`, `camera`, `mood` (emotional tone of the image), `visible_characters`, `background_people` (unmarked people), `props` (objects that matter and who holds them) and `notes`. Each entry of `visible_characters` is one character the user marked in the first frame, with `character` (name) and `character_context_id` (the context item, so every description is linked to a character record), `appearance` (visible outfit and hair only), `position`, `pose`, `expression` (the face as drawn), `emotion` (what it reads as, with strength), `gaze` (what the character looks at, naming other characters) and `action` (starts with the activity: standing, sitting, walking ...). Text fields refer to marked characters by name. Since 2026-11-16 (`contract: "frame-v2"`) each entry also has `pose_detail`: `body_pose` (standing, walking, running, sitting, lying, crouching, kneeling, leaning, jumping, other, unclear), `body_yaw`, `head_yaw` and `head_pitch` (whole degrees in steps of 15; yaw 0 faces the camera, positive turns toward the image's right, plus or minus 90 is profile, 180 the back; pitch negative looks down; null when not visible), `eye_gaze` (`up_left`, `up`, `up_right`, `left`, `center`, `right`, `down_left`, `down`, `down_right`, `closed`, `not_visible`, `unclear`), `gaze_target` (a character name with `gaze_target_id`, `camera`, `off_screen`, `object` with `gaze_object`, `none`, `unclear`), the derived `body_view`/`head_view` (`front`, `three_quarter_left|right`, `profile_left|right`, `back_three_quarter_left|right`, `back`), `frame_fill` (the box's height as a share of the frame), `flags` (disagreements the app calculated, such as a gaze target on the other side of the head's turn; they never change a value), `coerced` (fields whose word the app had to map) and `edited` when a person corrected it. A character the model skipped has `{"status": "missing"}`. Older results have no `pose_detail`. Results written before 2026-11-12 lack `mood`, `props`, `emotion` and `gaze`; older ones still may carry `other_visual_details`, `uncertainties` or `identity_evidence`.

`video_analysis` (written until 2026-11-18) is a motion direction when its content has `contract: "direction-v1"`, `"direction-v2"` or `"direction-v3"` (current runs write `direction-v3`). `direction` is the merged view for the whole cut: `summary`, `camera` (`movement` is one of static, pan left/right, tilt up/down, zoom in/out, push in, pull out, tracking, handheld, other, joined with " → " when it changes; `detail`), `characters` and `end_state`. Each character has `character`, `character_context_id` (null for an unnamed person, who gets a short visual label), `activity` (standing, sitting, walking, running ...), `travel` (movement through the picture, or `none`), `motion` (body movement, or "holds still"), `speaking` (`yes`, `no` or `unclear`: whether the mouth visibly moves as in speech), `emotion` (over the cut, with changes) and `end` (place and posture in the final frames). `direction-v3` adds `gaze` (where the eyes and head go and when they shift, absent when the gaze holds), `objects` (what the character touches, holds or moves, with what happens to it) and `state_correction` (`first_frame` and `clip`, only when the clip's first state differs from the first frame's `pose_detail.body_pose`: the video decides the state during the clip), and each event may carry a `kind` (`body`, `gaze`, `mouth`, `expression`, `object`, `travel`, `camera`, `other`). Current runs detect characters only in the first frame, so the video model reports end state without a last-frame box confirmation. Historical directions may include `end_state.in_frame` and `in_last_frame` when a last-frame box confirmed presence; absence of those fields is not evidence of leaving. `windows` keeps each analysis window with its own `overview`, `camera`, `characters` and timed `events` (`subject` is a character name with `character_context_id` when it could be linked). The model is given the first frame's description of marked characters and the transcript's speaker timing (no words), so names in the motion direction match the first frame. `GET /api/v1/cuts/{cut_id}` returns the same direction as `motion`, with events of all windows on one clip-relative timeline. A `video_analysis` without `contract` predates motion directions and only has per-window `overview` and `events`.

`consistency_summary` (text step, written from the first frame, the keyframes and the performance beats, or for older cuts the video analysis) has `summary`, `clear`, `confusing` and, since 2026-11-16, `questions`: at most five multiple-choice decisions, each `{id, topic, character, question, options: [{id, text}], recommended, why}` (`topic` is `pose`, `gaze`, `state`, `speaking`, `emotion`, `position`, `identity`, `camera`, `objects` or `other`; `recommended` is an option id or null). Since 2026-11-19 a review written by a model that could read images also looked at pictures of the cut (first frame, keyframes, a strip of frames per spoken line, character reference crops) and starts with `visual_check`: at most twelve `{character, picture, source, claim, seen, verdict}` comparisons of a stored reading with the picture of that moment (`picture` is a label such as `F3` or `Line 12.30-13.50s`; `source` is `first_frame`, `keyframes`, `beats` or `transcript`; `verdict` is `contradicts`, `unclear` or `agrees`, contradictions first). A review without pictures has no `visual_check`; the result's settings say `vision: true|false`, and the stored evidence lists the pictures sent (`pictures.sent`) as references, never pixels. The review's evidence also carries `episode` (the neighbouring cuts, the transcript just before and after the cut, and how each voice label heard in the cut is linked to characters across the episode). Results written earlier have `human_review` and `recommended_checks` text instead and no `questions`. A person answers in the cut's saved answers (`GET/PUT /api/cuts/{cut_id}/brief-instructions`), one bullet per decision written as `- Topic (Character): chosen text`; the answers are confirmed facts, not a field of the result. The Cut summary (`Cut summary` result, Markdown) is a performance director's brief written from the first frame, the beats and keyframes (or the older motion direction) and those answers only. Since 2026-11-18 it has the sections Scene, Opening Frame, Performance Beats (one time-coded line per beat and character: body, face, gaze, mouth with its delivery, intent), Acting Notes and Continuity & Constraints, at most 6144 bytes. It holds no dialogue text or speaker turns; a beat names only the mouth action and the delivery. Summaries written from 2026-11-16 have the four sections Scene, Opening Frame, Animation Timeline and Continuity & Constraints, older ones also a Dialogue section; dialogue is grouped when a sequence is created.

In a beat, a line's `delivery` says how it is played. For older cuts, `speaking: no` while the transcript links a line to that on-screen character usually means an inner voice or narration; a line whose speaker is not in frame is an off-screen voice. Emotion is read from the picture; no acoustic analysis is made.

The rest of this section is about the stored video analysis. It accepts any valid JSON value, so its structure may vary. When an event has a usable in-window interval, derived episode-relative timestamps accompany the model’s clip-relative times. Model-provided times are unverified and may be unordered, overlap, or fall outside the window; they are retained rather than rejected. Cuts of up to six seconds are watched as one clip; longer cuts are partitioned into analysis windows, so events crossing windows can be split (each window is told what the previous one reported). Visual models process silent video and cannot establish who is audibly speaking; speaker and character links come from transcript evidence and need verification. Subtitle lines are model readings and can be wrong; they are reference evidence and should not be reproduced as visual content.

`GET /api/jobs/{job_id}/analysis-windows` returns the recorded source timing, preparation settings, model revision and structured output for each completed video window, including windows saved by an incomplete run. Retry copies these checkpoints and uses them when their timings and model revision still match. Temporary video files can be removed without losing the metadata or observations.

## Subtitles

The user extracts the burned-in subtitles of an entire episode in one step, after audio transcription (`POST /api/episodes/{episode_id}/subtitles` with the required `language`; every subtitle in the video is in that single language and the model is told so). `GET /api/v1/episodes/{episode_id}/subtitles` returns the saved `language`, the current `run` (status, detected strip as fractions of the frame height, diagnostics, model) and all current `lines`; `?history=true` also lists earlier runs. A line has episode-relative `start_time` and `end_time` (resolution about 0.125 s), the `text` as read with displayed lines separated by a newline, and `confidence` (`high`, or `low` when some characters were hard to read). Lines belong to the episode and are not tied to a cut: `GET /api/v1/cuts/{cut_id}` and `/api/cuts/{cut_id}/analysis-context` return `subtitles` with the `language`, the `strip`, and the `lines` overlapping the cut, where `crosses_cut` marks a line that starts before or ends after it. `extracted: false` means the extraction has not been run; empty `lines` with `extracted: true` means no subtitle overlaps the cut. A reading that was not in the stated language is dropped rather than stored. Subtitles may paraphrase or translate speech and are not audio evidence.

In the composition view, `subtitles` are the episode lines that overlap the cut. `lang` is the episode's subtitle language code (or its name) and `t` is the clip-relative second at which the line appears, clamped to 0 when it started before the cut. Cuts analysed before the episode was extracted keep their older per-cut readings in this field until it is.

Use `GET /api/v1/episodes/{episode_id}/brief?from=1&to=14` for an inclusive range of one-based active cut numbers (maximum 500). Each cut includes episode-relative `[start_time, end_time)` timings, IDs, current overlapping transcript segments with speaker labels and character context IDs, model-generated production sections with qualitative confidence, and relative audio and first-frame URLs. Transcript segments crossing a cut retain their original boundaries. Empty dialogue does not prove silence. Null sections indicate missing data; run visual analysis again to populate structured fields for older summaries or summaries edited as free text. The action beats and character descriptions are model-generated observations and may be uncertain; use source media for verification.

### Composition view (in development)

`GET /api/v1/episodes/{episode_id}/brief?from=44&to=68&view=composition` projects the saved visual results, transcript, subtitle lines and character detections into cut records. It does not invoke a model. `shot` uses standardized shot-size, angle and camera labels when they can be extracted (the camera movement, its `direction` and `camera_detail` come from the motion direction); `mood`, `props`, `action` (what happens), `subjects`, clip-relative `beats`, `end_state`, merged `dialogue` and sampled `subtitles` are based on existing observations and may be incomplete or incorrect. A subject carries its first-frame `emotion` and `gaze` and, when the cut has a motion direction, a `motion` object (`activity`, `travel`, `motion`, `speaking`, `emotion`, `end`). With a motion direction, `end_state.subjects` lists an opening subject as `left frame` when the video analysis says so, plus the `motion` of anyone who is not an opening subject (`entered frame` when their travel says they enter). Historical saved box confirmations remain represented in their original results. A cut is ready with an `initial_frame` and its motion: for a cut with a `keyframe_analysis`, `performance_beats` built from it (the projection reads the keyframes as a motion direction); a cut without one needs a motion-direction `video_analysis`, and cuts whose video analysis predates motion directions also need their stored `last_frame`, which then supplies `end_state` and `last_frame_id` as before. A cut whose beats are being written is not ready. `identity` distinguishes confirmed user labels from likely matches. Subtitle `t` is when the line appears, at about one eighth of a second. The current projection may omit details and exceed the intended 2 KB-per-cut target; it is not yet a complete composition contract.

`duration` is the cut length in seconds. Beat and utterance times are relative to the cut start. The default omits episode-relative boundaries; request them with `fields=start_time,end_time` when needed. `ready_count` and `pending` refer to the entire requested range. An unready cut contains identity and readiness metadata rather than a partially populated shot. `only_ready=true` filters unready cuts. `updated_since` accepts a timezone-aware ISO 8601 timestamp and is inclusive at millisecond precision; readers should use their own conservative query watermark and deduplicate by cut ID. When projection code changes, startup advances cut watermarks so an incremental reader can discover changed output; unchanged records may be returned again. The response is a database snapshot; file availability can change independently. `fields=shot,dialogue` selects cut keys, retaining `id`, `cut_number`, and `ready`. `include=` accepts comma-separated `initial_frame`, `keyframe_analysis`, `performance_beats`, `last_frame`, `video_analysis`, `subtitle_ocr`, `consistency_summary`, and `dialogue_segments` to add the original structured results or overlapping segments. Includes can greatly increase the response size. Invalid names return 422.

Dialogue is preserved even when it makes a cut exceed the size target. In particular, a single transcript segment can itself be larger than 2 KB; the composition view does not truncate it to meet the target.

In `beats` and `end_state.subjects`, an integer `subject` is a zero-based index into the same cut's `subjects`; a string identifies a subject that cannot be linked uniquely. With `fields` that excludes `subjects`, those indices are expanded back to names so the selected fields remain self-contained.

Depth defaults to `mid` when the source does not specify a depth. The end-state comparison does not treat a change to or from that default as established movement; uncertain depth changes are omitted from the end state.

Use `/api/analysis-results/{initial_frame_id}/frame` for the analyzed first-frame JPEG, `/api/cuts/{cut_id}/frame/last` for the cut's last frame (`/api/analysis-results/{last_frame_id}/frame` on older cuts that still have an analyzed one), and `/api/v1/cuts/{id}/audio` for the exact-cut WAV. URLs are relative to the server origin. A missing audio or frame file can still yield 404 or 503. The `view`, `include`, `fields`, `only_ready`, and `updated_since` parameters also apply to the export POST. Composition exports contain `cut-NNNN-UUID-initial.jpg` and, with `include=last_frame`, `cut-NNNN-UUID-last.jpg`, extracted at the original video's resolution. The manifest reports extraction errors, `audio_seconds` when audio was extracted, and `has_speech` based on current overlapping transcript segments. Exports run independently of episode analysis jobs and are excluded from cancellation of queued analysis jobs.

To retrieve the brief and assets together, `POST /api/v1/episodes/{episode_id}/brief/exports?from=1&to=14`, then poll `GET /api/v1/brief-exports/{job_id}` until it is `done` or `failed`. Download the returned `download_url` when done. The ZIP contains `brief.json`, `manifest.json`, per-cut sample-aligned WAV audio (including cuts shorter than two seconds), and JPEGs at the original video's resolution when available. If the original video is missing, the manifest reports the missing frame instead of substituting a smaller proxy or thumbnail. The manifest records missing assets and extraction errors. The brief is snapshotted when the export is queued; assets may become unavailable before processing. Audio is from prepared episode audio, and silent episodes do not provide WAV files. Previously completed downloads retain their original contents; older queued exports that reference a saved analysis image retain that image.

## Sequences: directed short videos (contract `sequence-v2`)

A **sequence** is a contiguous range of an episode's active cuts, at most 180 seconds long, that the user had directed as one short video played on the **original audio**. It is the layer to read when generating video: it holds the shot list, each shot's initial frame, audio interval, dialogue with speakers, and the final MiniMax H3 prompt. Cuts and their analysis are untouched by it.

Direction has three results, each a revision chain with origin `model`, `manual_edit` or `assistant_edit` and no approval status: the **bible** (story, spoken language, scenes, characters with anchors and outfits, `voices` deciding who owns each voice label, continuity rules), the **plan** (one shot per cut, in order; shots are never merged, and only a cut longer than 15 seconds is divided at pauses into consecutive parts of one take; at a hard cut that falls inside speech the boundary either stays on the cut, dividing the phrase, or moves at most 3 seconds into the silence just before or after the phrase so that it stays in one shot), and one **shot** direction per planned shot, from which the app renders the prompt. An advisory **review** checks continuity.

### Read order

1. List `GET /api/v1/episodes/{episode_id}/sequences` and choose one by ID.
2. Read the digest, `GET /api/v1/sequences/{sequence_id}?view=digest` (about 5 KB): `ready`, `pending`, the flags, the bible's essentials, every issue (grouped), and one compact entry per shot. Generate only when `ready` is true and no issue has severity `error`.
3. For each shot you generate, read its slice `GET /api/v1/sequences/{sequence_id}?shot=N` (lean, a few KB): the shot with its opening edge, the speakers it uses and its issues. Narrow further with `fields=` (for example `fields=lines,voices,initial_frame`).
4. Take the prompt from the ZIP's `shot-NN-prompt.txt` / `shot-NN-prompt-template.txt`, or add `include=prompts` to the request.
5. Look at the pictures before you trust a description: `contact-sheet.jpg` for the whole sequence, then `shot-NN-initial.jpg`, `shot-NN-strip.jpg` and `shot-NN-last.jpg`.

Never read `view=full` whole unless you need every prose field: it is about four times the lean size.

### Views and conventions

`GET /api/v1/sequences/{sequence_id}` takes `view` (`lean`, the default; `digest`; `full`), `shot` (one-based index; 404 when it is not in the plan), `fields` (comma-separated shot keys; `index` is always kept) and `include=prompts` (adds `prompt`, `prompt_template` and `still_prompt` to the lean view). The digest takes none of the others. An unknown view, field or include is a 422.

- Each fact is stated once. Keys whose value would be null, empty or false are left out; `ready` and `check.ok` stay when false, and `written: false` marks a shot without a direction.
- One clock per shot. Shot times (`lines`, `voices`, `beats`, `subtitles`) are seconds from the start of that shot; `shot.at` is its start on the sequence clock and the top-level `start_time` is the sequence's start in the episode, so episode time = `start_time + shot.at + t`. `cuts[]` gives each cut's `number`, `id`, `at` and `duration` once.
- `speakers` maps ids (`SP1`…) to `{name, kind, character_context_id, speaker_labels}`; `kind` is `character` (a record), `narrator`, `voice` (a diarization label nobody resolved) or `unknown`. Lines and voices name the speaker by id.
- `provenance` gives `{id, origin, model_id, created_at, revision}` of the bible, plan, compilation (the reviewed dialogue), review and of each written shot (`shots` by index); `revision` is the position in its chain (1 = first).
- `subtitles` (top level) says whether the episode's burned-in subtitles were extracted and their `language`.
- Whatever the app guessed is labelled: `kind_guessed`, `linked_by: "name"`, `candidate` with a `confidence`, `description_source: "derived"`.

### What a shot contains (lean)

- `index`, `cut` (the cut this shot is; its picture is the only one shown), `part` (`[n, of]` for a cut longer than one take), `at`, `duration` (its length in the finished video). `generate_seconds` appears only for shots shorter than 5 seconds: generate that long (the prompt ends on a hold) and trim the result to `duration`. `source_cuts` appears only when the shot plays a neighbour's audio (a boundary moved to keep a phrase whole).
- `closes`: how the shot meets the next one (absent for the last shot); a shot opens with the previous shot's `closes`, and a one-shot slice adds it as `opens` (`{how: start}` for the first shot). `how` is `keep_cut` (exactly on the hard cut), `before_line`/`after_line` (moved by `shift` seconds into the silence around the phrase `keeps`), or `continuation` (the next part of the same long cut). `splits` lists the lines the edge divides; `reason` and `by` (`director`, `app`, `user`) explain the choice. `placed: true` marks a boundary the user placed by hand on the Dialogue timeline: `before_line`/`after_line` then only say it sits earlier or later than the hard cut, it may divide speech (see `splits`), and it is final.
- `scene`, `intent`, `camera` (`move`; `amplitude`, `speed`, `detail` when it moves), `beats` (`start`, `end`, `action`; the hold the app adds to a short shot is `{start, end, hold: true}`), `continuity.from_previous`.
- `initial_frame`: `description` (the prompt's `<Picture 1>` line) and `description_source`. `observed` is the analysed first frame of the shot's cut. `derived` is a later moment of the cut that was never analysed (the next part of a long cut, or a cut whose first moment the previous shot borrowed to finish a phrase): the director inferred it, `derived_from` says from what, and it can be wrong. Check it against `shot-NN-initial.jpg`. `continues_previous_shot: true` means the last generated frame of the previous shot may serve as the opening image instead.
- `voices`: how each speaker is heard, as ranges `{speaker, from, to, delivery, subject, fixed}`. `on_screen`: visible with the mouth visible, lip-synced. `off_screen`: not in the picture. `inner_voice`: visible, the mouth does not move for the words. `narrative`: too far for lip sync; the words play over the picture. `subject` is the `<Subject N>` that carries the voice; `fixed: true` marks ranges the user decided. A line takes its speaker's range at its midpoint.
- `lines`: `{id, speaker, t0, t1, text, by}` with the words verbatim; `by` says who decided the speaker (`reviewed`: the user reviewed the dialogue; `transcript`: the user's link; `director`: the bible; `unknown`: nobody). A line divided by a shot edge appears in both shots with its own words (`crosses_start`, `crosses_end`). A line nobody attributed may carry `candidate` `{character_context_id, name, confidence: low|medium, reason}`: a heuristic from who is on screen, who visibly speaks and who speaks the neighbouring lines. It is advice; Framewise keeps no voice-match score, so it is never `high`, and the stored decision stays unknown.
- `line_map`: line id to template slot (`L5` → `1.1`), see below.
- `subjects`: `{n, name, kind, character_context_id, context_id, picture, linked_by, record_name, kind_guessed}` for each `<Subject n>`. `linked_by: prompt` means the prompt itself names the record and attaches its sheet as `<Picture picture>`. `linked_by: name` means the app matched the name to a record afterwards: the prompt has no sheet for that character (issue `no_sheet`). Other subjects have a guessed `kind` (`person`, `object`, `place`, `unknown`, from the opening frame's analysis); `scenario` is the place of a scenario note.
- `pictures`: entry N is `<Picture N>`: `initial_frame` first, then `character_sheet` and `scenario` entries naming their `subject`. `<Audio 1>` is always `shot-NN.wav`.
- `subtitles`: burned-in subtitle lines overlapping the shot, on the shot's clock, with `crosses_shot` when a line starts before or ends after it. They are for meaning only; the shot must not show text.
- `check`: `{ok}` plus `errors`/`warnings` when there are any; `stale` lists what changed since the shot was written (`plan`, `bible`, `evidence`).

`view=full` adds `prompt`, `prompt_template`, `still_prompt`, `still` (`shot`, `placement`, `subjects`, `layout`, `setting`, `lighting`; `placement` says in words where each character is, which way torso and head face and what the eyes look at, and is absent from shots written before 2026-11-16, as is its "Placement and gaze" row of `still_prompt`), the stable `key` (the episode interval in milliseconds), `soundscape` (only on shots written before 2026-11-15; the prompt's sound section now tells the generator to follow `<Audio 1>` exactly and describes no ambience), subject `anchors`/`keep`, `continuity.to_next`, `check.stats`, `initial_frame.at` and per-revision `generation_seconds`.

### Issues

`issues` is one list, most severe first: `{shots, line, severity, kind, text}`. An issue that reads the same in several shots is listed once with all of them in `shots`; without `shots` it concerns the whole sequence. `error`: fix it in Framewise before generating. `warning`: decide or look before generating. `info`: how to generate.

| kind | severity | meaning |
|---|---|---|
| `cuts_missing`, `cuts_changed`, `plan_problem` | error | The cut range changed; the sequence must be directed again. |
| `not_written`, `stale`, `check_error` | error | No usable prompt for that shot yet. |
| `template_unavailable` | warning | The stored prompt no longer renders from its direction; no template. |
| `open_question` | warning | The director (shot or bible) could not decide something from the evidence. |
| `review` | warning | A continuity problem the review found, with its suggestion. |
| `unknown_speaker` | warning | Nobody decided who says a line; see its `candidate`. |
| `derived_frame` | warning | The initial frame description is derived, not observed. |
| `no_sheet` | warning | A known character is in the prompt without a character sheet. |
| `missing_reference` | warning | Framewise has no reference image of a character the prompts name. |
| `check_warning` | warning | A format advisory of the H3 check. |
| `padded_shot` | info | Shorter than 5 s: generate `generate_seconds`, trim to `duration`. |
| `unlinked_subject` | info | A person in the prompt has no record. |

### Prompt templates for dubbing

`prompt` is the final H3 prompt in the six-section FastH3 OmniRef format, starting at `subject_definitions:`, with the spoken words and their times. Generating the same shot in another language needs other words and other times, so each written shot also has `prompt_template`: the same text with `{language}` for the spoken language, `{line 1.M}` for each line's words, and `{start 1.M}` / `{end 1.M}` for the times taken from a line. Beat ranges and every other time are left as written. `1` is the shot's one reference audio (`shot-NN.wav`) and `M` is the line's order by start time among the shot's lines; `line_map` maps sequence line ids to these slots. `{duration 1.M}` is reserved for the consumer (the app writes no line duration). Times use the prompt's `MM:SS.mmm` form. The app renders the template from the stored direction exactly like the prompt, and keeps it only when filling it with the shot's own words and times gives the stored prompt back byte for byte; otherwise it is absent and the issue `template_unavailable` says why. A silent shot's template is its prompt.

### Download

`POST /api/v1/sequences/{sequence_id}/exports` (optional `include=sequence_audio,references,clips`) snapshots the full document and queues the ZIP; poll `GET /api/v1/brief-exports/{job_id}` until `done`, then download `download_url`. This is the only call that changes anything. The ZIP holds:

- `sequence.json` (the lean view, compact), `overview.json` (the digest), `manifest.json`, `contact-sheet.jpg` (every shot's initial frame with its number, cut and start), and `sequence.srt` (the range's burned-in subtitles on the sequence clock, when there are any).
- Per shot: `shot-NN.wav` (the exact interval of the original audio), `shot-NN-ref.wav` (only for shots shorter than 5 s: the original audio from the shot's start for `generate_seconds`, so the shot's own audio followed by what really comes after it, with silence only where the episode audio ends; for generators that need audio as long as the video; the prompt still names `shot-NN.wav`), `shot-NN-initial.jpg` and `shot-NN-last.jpg` at the original resolution (the last frame of the shot's own picture: a shot that plays on into the next cut's audio never shows that cut), `shot-NN-strip.jpg` (about one frame per second of the shot's own picture, each labelled with seconds of the shot, to check the beats), `preview/shot-NN.jpg` (640 px wide), `shot-NN-prompt.txt`, `shot-NN-prompt-template.txt` and `shot-NN-still.txt` (a prompt for the opening still) once the shot is written.
- `include=sequence_audio`: `sequence.wav`, the whole range. `include=clips`: `shot-NN-clip.mp4`, a silent clip of the shot's own picture at most 360 lines high, as a motion and pose reference. `include=references`: `references/characters/<character_context_id>.jpg` (a crop at the original resolution of the character's largest saved gallery reference, else of the largest manually labelled box in these cuts), `references/scenes/<scene id>.jpg` (the first frame of the scene's widest-framed cut) and `references/voices/<character_context_id>.wav` (the chosen voice sample; every other sample of that character is `<character_context_id>-<sample>.wav`).

`manifest.json` has `contract`, `sequence_id`, `job_id`, `queued_at`, `exported_at`, `sequence_updated_at`, `include`, `files` (every file with `bytes`, `sha256`, `kind`, `shot`, `source`, and `seconds`, `audio_seconds`/`continued_seconds`/`silence_seconds`/`padded_seconds` or `time` where they apply; for `-ref.wav`, `audio_seconds` is the shot itself, `continued_seconds` the original audio after it, `silence_seconds` only appears when the episode audio ended first, and `padded_seconds` the total), `references` (per character every crop candidate with the chosen one and why, per scene how its frame was chosen, per voice every sample with `ranges`, `seconds`, `preview_available` and the chosen one), and `errors` (each asset that could not be made). A missing asset is reported there and never replaced by a thumbnail or another file.

The per-shot routes `GET /api/v1/sequences/{sequence_id}/shots/{index}/audio` (`?pad=true` continues with the original audio after the shot up to `generate_seconds`, like `shot-NN-ref.wav`), `…/shots/{index}/frame` (the initial frame at the original resolution) and `GET /api/v1/sequences/{sequence_id}/audio` remain for single files.

### Changes from sequence-v1

`sequence-v1` is retired. `prompt`, `still_prompt` and `still` moved to the ZIP's text files, `view=full` and `include=prompts`. Shot `start_time`/`end_time`/`t0`/`t1` became `at` + `duration`. `cut_ids`, `cut_id`, `initial_frame.cut_id`/`cut_number`/`frame_url`/`file` and `audio` were dropped (ids are in `cuts`, files follow fixed names). `trim_seconds` is implied by `generate_seconds`. `merged` and `staging` are gone. `fixed_voices` became `voices[].fixed`. Each dialogue line's speaker fields moved to `speakers`, and its `delivery`/`subject` come from `voices`. `opens` is the previous shot's `closes`. `continuity.to_next` is full-view only. `open_questions`, `review.issues` and `check` problems became `issues`. `result` became `provenance.shots`. `references` became `pictures` plus `subjects`, and `initial_frame.strategy` became `description_source`.

Model output can be wrong: voices decided by the director, derived frame descriptions, candidates and open questions deserve a look before generation. For clients allowed to edit (AI Director is not), `PUT /api/sequence-results/{result_id}` appends a hand revision of a bible, plan or shot direction; it is validated like model output and a shot is rendered and checked again (422 lists the problems, 409 means a newer revision exists).

Local and OpenRouter text outputs record `settings.provider` (`local` or `openrouter`), `settings.summary_generation_seconds`, optional `settings.usage` token counts and, for the pinned local model, `settings.model_revision`. These values are absent for older runs or where the provider did not supply usage; do not infer token counts from text length. Visual results use `provider: local` and may record `generation_seconds` and model token counts when available.
