# Model integration plan

## Single-cut pipeline

Newly queued single-cut jobs use a separate checkpointed pipeline. WeVisOne localizes subtitles in selected frames and performs OCR when transcript segments overlap; its predicted boxes are passed to the visual models as uncertain positions. A local Qwen3.5-27B Q4_K_M GGUF with its BF16 vision projector produces structured initial and final frame descriptions through an isolated ROCm llama.cpp server. Qwen3-VL-8B-Instruct analyzes silent, aspect-preserving cut windows sampled at the configured FPS. Visual jobs do not infer audio or identify a speaker from subtitles. Transcript and deduplicated subtitle OCR are combined with the visual evidence by a separately queued local or OpenRouter consistency summary; all outputs retain revision links.

The inference worker processes GPU models sequentially and releases their memory between phases. `compose.inference.rocm.yml` mounts the Qwen3.5 model, matching projector, llama.cpp runtime and Qwen3-VL-8B weights read-only. The runtime and both new models must be installed before single-cut analysis can start. New batch jobs use the same visual-only workflow as single-cut jobs; previously queued jobs retain their original workflow. The separate audio worker can use the GPU at the same time, so concurrent transcription and inference may compete for memory and throughput. ROCm compatibility and the larger checkpoints require actual GPU inference validation before treating this path as production-ready.

The requested [WeVisOne-VL paper](https://huggingface.co/papers/2610.31329) and [official implementation](https://github.com/Tencent/WeVisOne-VL) describe image-level detection, referring localization, counting, OCR, segmentation, and matting. The official repository currently shows 2B and 4B variants and a Python 3.10 installation example. Its documented device choices include CUDA, NPU, and CPU; ROCm is not explicitly documented. Framewise has a separate pinned inference worker and download scripts. A host GPU test loaded WeVisOne and confirmed that free-form requests returned bounding-box output, so Qwen3-VL-2B-Instruct supplies natural-language captions while WeVisOne supplies configurable object detections. The container deployment still requires validation.

## Character detection and references

A separate queued `character_detect` job uses WeVisOne person detection on the first and last original-video frames. The user can label boxes, remove false positives, draw missed people, and explicitly save a labeled crop as a project reference. Qwen3.5 compares detections against up to two saved references per character; only a unique model-reported high-confidence match is applied, marked unverified. This is a qualitative model judgment, not a calibrated probability. When an individual cut is queued, the displayed named detections, including automatic labels, are captured as user-confirmed identity assignments for their respective boundary frames; users should correct or clear uncertain labels first. Their detector provenance is retained, and batch queueing does not imply confirmation. Labels do not establish presence or actions across the whole cut. References store source frame and crop coordinates so the original remains unchanged.

Single-cut analysis snapshots current non-stale boxes and labels and up to four reference examples for labeled or selected characters. The Qwen3.5 frame model receives labeled example images and the target frame; Qwen3-VL video analysis receives the frame-specific detection and label context as text. The consistency summary receives the same detection evidence alongside model outputs and transcript. Earlier runs and archived detection results are preserved; changing cut timing makes the latest detection stale until redetection. This comparison has been smoke-tested on the local ROCm runtime, but recognition accuracy must be evaluated on the user's footage and varied appearances.

## Intended place in the pipeline

1. Keep import, proxy creation, audio, waveform, chunks, and hard cuts in the small CPU app.
2. Hard-cut detection records first and last frame timestamps per cut; previews are recreated from the video on demand. Use these as initial visual inputs, retain the original as the quality reference, and sample additional frames per chunk as needed.
3. Run WeVisOne-VL detection and OCR and Qwen3-VL captioning on selected original-video frames. Store descriptions and parsed detection boxes with timestamps in SQLite. Masks are not generated. Both pinned checkpoints are mounted from persistent host directories.
4. A text model assesses individual visual and OCR claims with qualitative confidence before synthesizing a cut summary; its motion, action, and continuity suggestions are estimates, not measured temporal analysis. The documented WeVisOne-VL tasks alone do not establish motion or audio meaning.
5. Assemble the cut's input with `/api/cuts/{id}/analysis-context`: project synopsis, applicable character/world/scenario notes, overlapping chunk notes, current transcript overlap, and previous/next cut context. Freeze that input into `analysis_results.context_json` for reproducible retries.
6. Append model results to `analysis_results` with `origin='model'`, `model_id`, `job_id`, prompt, settings, and context snapshot. Do not overwrite existing results or human revisions. Store longer structured predictions or binary masks in dedicated artifact tables/files when an inference adapter is implemented.

Redetection archives unmatched cuts instead of deleting them, so their manual notes and model provenance remain available. A matching boundary can reactivate the same cut ID and its results.

## Device and deployment boundary

Keep a separate inference worker image for the selected ROCm or CUDA PyTorch runtime. Mount the same `/data` and `/models` volumes and pass `/dev/kfd` and `/dev/dri` for ROCm or the NVIDIA runtime for CUDA. Validate the chosen WeVisOne-VL version with the ROCm stack before enabling model jobs; the upstream quick start documents CUDA/CPU but does not establish ROCm compatibility. Do not install a CUDA wheel in the base app container.

The media worker now claims durable SQLite jobs with a renewable lease, heartbeat, attempt count, and queued settings payload. A separate inference worker should claim only its own pipeline kinds and preserve the same lease ownership checks before writing results. Keep media preparation idempotent so a restarted worker can resume safely. The adapter loads the mounted local weights lazily on the first job. The separate download script pins and verifies the cached files; the worker does not download model weights.

## Later audio and prompt work

`transcript_segments` stores timed text, speaker labels, optional links to character context records, a deletion marker, model/job provenance, and revision links. Human edits append a new revision; deletes append a tombstone, so model output can remain inspectable under history. The audio worker populates it and can suggest character links from voice references. The context endpoint includes current transcript segments overlapping each cut, except deleted segments, so audiovisual matching can start from aligned evidence.

The cut summary combines visual evidence and context for still-image and animation planning. Confidence is qualitative rather than a calibrated probability. Preserve each prompt version, the evidence used, and user edits. Output from generation services belongs in new artifacts and should not replace reference media.

## Local text consolidation

Run Settings separates visual analysis from text processing. Queue visual jobs first; queue text processing after they finish to create a consistency summary followed by a dependent Cut summary per ready enabled cut. Previous jobs keep their original snapshot and workflow. Each text queue snapshots its OpenRouter/local provider, thinking setting and evidence; cancelling a consistency job also cancels its queued dependent brief.

Select Local Qwen 3.6 35B A3B Q4_K_M or OpenRouter for summary jobs. The local model uses the existing inference worker and a worker-owned llama.cpp server with a 65,536-token context. The server is reused across queued text jobs and released before local visual analysis. Run Settings shows download/loading/generating state and allows keeping the model loaded or unloading it when idle. Qwen 3.6 thinking can be switched per run; the default thinking budget is 2,048 tokens (configurable with `QWEN36_THINKING_BUDGET`) so it leaves room for the answer. `QWEN36_CONTEXT_SIZE` controls the local server context. OpenRouter continues to use the selected OpenRouter model.

`scripts/download-qwen36.sh` resumes and SHA-256 verifies the pinned 20.4 GB GGUF before making it available under `.models/qwen3.6-35b`; `TEXT_MODEL_DIR` overrides the host directory. The ROCm Compose override mounts this directory read-only. Do not expose the local llama.cpp server outside the inference container. On the Radeon AI PRO R9700 host, the pinned model loaded with the default 65,536-token context and completed synthetic consistency and production-brief requests with thinking off and on. During that test, total GPU memory use was about 28.8 GB, including other allocations; it was about 6.8 GB after unloading. Requests near the context limit were not benchmarked. Long requests that exceed the configured context should fail rather than silently discard evidence.

New model-generated results record provider, model revision, elapsed generation time and any input/output/token details returned by the provider. Token usage is unavailable for older records and for model stages that do not supply counts; counts in retried requests include reported attempts. Time includes local loading when needed. Queued and interrupted jobs retain their settings snapshots and existing lease/revision checks.

## Individual visual stages and cancellation

Run Settings can queue subtitle detection/OCR, initial frame, video analysis, or last frame independently. Each stage is its own leased job and creates a new revision only for that result. Distinct stages for the same cut may be queued together; overlapping stages are rejected. The job snapshots the cut, settings, context, existing result revisions and, for an individually queued frame or video stage, any current subtitle result with matching cut boundaries. If no matching subtitle result exists, the visual stage runs without subtitle regions. A subtitle-only job performs OCR only when transcript segments overlap and does not run frame-model language classification.

Running single-cut visual jobs can be cancelled from run history. Video generation checks cancellation during decoding; subtitle detection/OCR stops between model calls, and frame requests stop when their cancellation checks run. In-flight setup or media operations may finish before cancellation is observed. Cancellation revokes the job lease so late output cannot be saved. Retry uses the saved settings and reuses completed stages and video windows; rerunning an individual stage separately starts that stage anew. Legacy visual jobs keep their original cancellation behavior.
