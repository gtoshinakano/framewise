# Agent guide

Framewise is a local-first video analysis app. Preserve the hierarchy `Project → Episodes → Original Video` and the original upload. Sequences are an optional layer above cuts: a range of cuts directed as one short video (see the code map). The working flow is import → background media preparation → user-triggered hard-cut detection → timeline playback and editable cut notes, with optional queued visual analysis (first frame, then what changes between the cut's keyframes, then the performance beats a text model compiles from them), audio transcription, and an episode-wide burned-in subtitle extraction that the user runs after transcription. Do not download models without a task requiring them.

## Code map

- `backend/app/main.py`: FastAPI endpoints and input validation.
- `backend/app/db.py`: SQLite schema and connections. Database and media persist under `DATA_DIR` (`/data` in Docker).
- `context_items` stores project or episode scoped chapter, character, world, scenario, object, and general notes for inference prompts.
- `analysis_results` stores per-cut text with revision links and optional model/job provenance; `transcript_segments` stores timed audio text and speaker/character links with revisions. Default reads return current results and current non-deleted transcript segments; `?history=true` returns the full revision chain. All current results and overlapping non-deleted transcript segments are usable for analysis. Results and transcripts have no approval status; do not add one to the database, API, prompts, or UI. `/api/cuts/{id}/analysis-context` supplies adjacent cuts and their current results, applicable context items, chunks, transcript overlap, and the `subtitles` object (`extracted`, the episode's subtitle `language`, the `strip`, and the subtitle `lines` overlapping the cut with `crosses_cut`). Transcript deletion revisions retain a separate `deleted` flag.
- `backend/app/worker.py`: one background media worker claims jobs from SQLite. Claims use a 60-second renewable lease, three-attempt interruption limit, and queued settings snapshot. Queued and interrupted jobs survive process restarts.
- **Queue and run history (2026-11-15):** `backend/app/job_kinds.py` is the registry of job kinds. Each `jobs.pipeline` has one `Kind` that says:
  - its label;
  - whether it is GPU work (counted) or CPU media work (listed only);
  - when it can be cancelled while queued or running, and whether it can be retried;
  - which cuts, sequence or audio range it works on;
  - how many GPU steps it holds (visual analysis is cuts × stages, every other kind one per job);
  - its `keys`: a later run with the same keys, or a retry, deals with a failure.
  **A new pipeline needs an entry there**; `tests/test_runs.py` checks every pipeline a worker claims.
  `backend/app/runs.py` (no FastAPI) builds the queue from it. `summary` is the header counter: this episode's GPU steps during its current busy period, sent with `GET /api/episodes/{id}/status` as `queue`. It also provides `queue_state`, `history` (paged by rowid), and `attention` (failures that are not dismissed and not resolved). Queries read a slim payload built by SQLite (`SLIM`), never the stored contexts.
  `backend/app/queue_api.py` holds the routes:
  - `GET /api/episodes/{id}/queue` and `GET /api/episodes/{id}/runs`;
  - `POST /api/episodes/{id}/queue/cancel {include_running, group}`;
  - `POST /api/jobs/{id}/dismiss` and `POST /api/episodes/{id}/queue/dismiss-failures` (both set `jobs.dismissed_at`);
  - `POST /api/chat-gateway/requests/{id}/cancel`.
  **Cancelled is its own job status, never a failure.** Every cancel goes through `worker.cancel_jobs`, followed by `worker.after_cancel` once committed. It:
  - writes `status='cancelled'`, keeping `stage='Cancelled'` because text handlers poll it;
  - cascades to jobs whose `payload.depends_on` lists the cancelled job. Every kind waits for all of its dependencies to finish successfully. A failed or missing dependency also cancels its queued dependents.
  A running job keeps its `lease_owner`, and `worker.heartbeat` keeps renewing it until the worker lets go, then releases it. Until then the queue reports the job as `stopping`, because the GPU is still busy.
  Readers that use "failed" in a workflow sense (resume a checkpoint, retry, chain held back) check `IN ('failed','cancelled')`. `last_job_failed` and the queue count only real failures.
- `chunks` stores timed working segments for long videos; cuts are independent visual boundaries and may cross chunk edges.
- `backend/app/prompt_context.py` slims what text prompts (consistency summary, review answers, Cut summary) receive: transcript lines are only start/end, text, `speaker_label`, `character_name` (current, non-deleted); neighbouring cuts contribute only their Consistency summary; first-frame and motion-direction results are sent as compact objects (`frame_view`, `video_view`); detections drop recognition scores, `match_reason`, model names and ids; results drop ids, kinds and model names. Route any new prompt input through it instead of sending rows. The API and `/api/v1` keep the full context.
- `backend/app/inference_worker.py` runs `TEXT_JOB_CONCURRENCY` (default 2) local text jobs at once: the main loop plus `text_lane` threads that claim only `regen`, `consistency_summary`, `review_answers`, `performance_beats` and `sequence` (`worker.TEXT_PIPELINES`, which `claim_job` lets share an episode), each holding a `chat_session` so visual jobs release the GPU only after they finish, and the Qwen3.6 server runs with that many `--parallel` slots (`QWEN36_CONTEXT_SIZE` is split between them, 32768 each by default). Restart the inference worker after changing either setting. **The text server also loads the vision projector (2026-11-18)** so chat can read images: `local_text_runtime._launch` adds `--mmproj` (`QWEN36_PROJECTOR_PATH`, `projector_path`) to either variant when the file exists and `QWEN36_TEXT_VISION` is not `0` (`vision_enabled`); if the server exits while starting with it, `_ensure` starts it again without and remembers the reason per variant in `vision_failed` (text jobs are never blocked by it), and `runtime.vision` says whether the running server loaded it (confirmed with `/props` `modalities`). `local_text_runtime.vision_status` gives the reason shown beside the provider. Whether `--mmproj` works together with the MTP flags in the bundled build and how much VRAM it adds were not measured on the GPU: check `local_text_model_state` after a restart. The text server has two interchangeable model files chosen by `text_generation_settings.local_model` (`standard` Q4_K_M, or `mtp`, the Unsloth UD-Q4_K_M with the multi-token-prediction head that `llama-server` uses for `--spec-type draft-mtp`; `local_text_runtime.VARIANTS`, `QWEN36_MTP_MODEL_PATH`, `QWEN36_MTP_ARGS`, `scripts/download-qwen36-mtp.sh`). The worker publishes `local_text_model_state.variant` and `variants_json` (installed/downloading), `PUT /api/text-generation-settings` refuses an uninstalled variant, and `LocalTextRuntime` switches only when `can_switch()` (no request in flight via `runtime.request()`, no other chat session); text lanes claim nothing while `switch_pending()`. `chat_json` re-asks `runtime.request()` for the server address on every attempt and saves `model_variant`, `predicted_n/ms`, `decode_tokens_per_second` and `draft_acceptance` in each result's `usage`; `GET /api/text-model-comparison` averages them and the text engine dialog shows the table. Never hardcode the model revision: use `local_text_runtime.revision_for(usage['model_variant'])`. It also claims visual `analyze`, `regen` and `subtitles` jobs. `POST /api/cuts/{id}/regenerate-summary` queues a revision of the `Cut summary` result and fails if that result changed while queued; the worker also supports older queued animation-prompt jobs. Analyzed frames are saved as `analysis/{result_id}.jpg` beside the original so `/api/analysis-results/{id}/frame` can serve them under detection overlays. `SUBTITLE_RULE` prevents treating subtitles as objects to reproduce. The UI lives in `AnalysisDialog.tsx`, `DetectionPreview.tsx`, `ResultEditor.tsx`, and `AnimationPromptPanel.tsx`.
- `backend/app/remote_text.py` adds a llama.cpp server on another LAN PC as extra text workers (setup: `docs/remote-text-server.md`). Settings live in `remote_text_server` (one row: `enabled`, `base_url` typed by the user because the PC has a dynamic IP and no host name, Bearer `token` (llama-server `--api-key`), `parallel`, `routes_json`, `assistant_fallback`); the token is never returned (`has_token`; an omitted token keeps it, an empty one clears it). `GET/PUT /api/remote-text-server`, `POST /api/remote-text-server/test`; UI `RemoteTextServer.tsx` in the Text engine dialog, helpers in `remoteText.ts`. One base URL serves several models (router mode or llama-swap) and the request's `model` field picks one. `routes_json` maps each `worker.TEXT_PIPELINES` entry to `local` (default), `remote` (remote lanes only) or `any` (first free lane) with a remote model; routing applies only to jobs queued with the local provider (`worker.JOB_TEXT_PROVIDER_SQL`, `claim_job(remote_only=, local_provider_only=)`) and is read at claim time, never snapshotted. The inference worker runs `remote_monitor` (probes `/health`, `/v1/models`, `/props?model=` every 10 s into `remote_text_state`) and `remote_text.MAX_LANES` `remote_lane` threads; lane *i* works while `i < parallel` and the state is online, runs the ordinary handler inside `remote_text.bind(cfg, model)`, and never holds a chat session or touches `LocalTextRuntime`, so remote text work continues while visual jobs own the GPU. **Same-episode rule (2026-11-16):** `claim_job` holds an episode for one non-text job at a time, which used to keep a queued text job (even for the remote lane) waiting behind a running `analyze` job of that episode. A remote lane now claims with `remote_lane=True`: its lease owner starts with `worker.REMOTE_OWNER` (`remote:`), it starts beside a running `worker.ALONGSIDE_REMOTE` job (only `analyze`), and `analyze` jobs are not held by a job with such an owner. Every other pipeline still holds the episode alone in both directions; extend `ALONGSIDE_REMOTE` only for jobs that neither need the text job's inputs nor change cuts. Under a binding `chat_json` posts to the remote, records `usage.model_variant = 'remote:<model>'` and `endpoint: 'remote'` (`revision_for` returns that string), and `sequence_evidence.slot_tokens` uses the model's reported per-slot context. A connection failure with a failing health check raises `RemoteUnreachable` (a `SummaryCancelled`, so handlers leave the job alone) and the lane requeues it with `worker.requeue_job` (attempt not counted). Cancel paths call `local_text_runtime.cancel_local`, which does nothing on a bound thread. Cut Assistance lists the remote as provider `remote` (`providers.RemoteLlama`), and `providers.gpu_fallback()` answers GPU-busy local turns with `remote_text.chat_model()` (the `assistant_fallback` model, else the first the server lists) when it is online, else OpenRouter free. **One pool of servers (2026-11-14):** this host (`TEXT_JOB_CONCURRENCY` slots) and the remote (`parallel`) are two servers in `remote_text.pool`, in-process counters shared by the lanes and the assistant thread. A pipeline with no saved route is `any` with `chat_model()` (`effective_routes`; a saved `local`/`remote` route still wins). `prefer` (`local`|`remote`) lets the preferred server's lane claim first (the other waits 1 s when it is free). Chat has priority: lanes take a job token (`pool.try_job`) before `claim_job`, which fails while a chat turn waits (`pool.chat_waiting`: a queued turn or an `auto` turn looking for a server) and limits jobs to `capacity - chat_reserve` slots per server (`chat_reserve`, default 1, saved in `remote_text_server` with `prefer`); the main loop applies it only to local-model text jobs. No running job is preempted. The `auto` chat provider (`providers.AutoServer`, default when the remote is online) uses `remote_text.pick_server()` (free slot, GPU not held, preferred first), waits with stage `Waiting for a free server`, and records `usage.server`. `assistant/runner.loop` runs each turn on its own thread (`MAX_CONCURRENT_TURNS`). Keep `TEXT_JOB_CONCURRENCY` one above the number of jobs you want in parallel. Restart the inference worker after changing `remote_text.py` or the lanes.
- `backend/app/chat_gateway.py` + `chat_gateway_worker.py` expose Qwen 3.6 to LAN clients as an OpenAI-compatible provider (2026-11-15, setup and limits in `docs/chat-api.md`): `GET /v1/models`, `POST /v1/chat/completions` (streaming, `reasoning_content`, tools passed through). The API process cannot reach `llama-server` (127.0.0.1 inside the inference worker, random port, stopped for visual work), so a request is a row in `chat_gateway_requests`; the inference worker (`start_chat_gateway`, `CHAT_GATEWAY_WORKER=0` disables it, up to `MAX_CONCURRENT` at once) claims it, runs it through `providers.AutoServer` (this host or the remote PC, chat priority in `remote_text.pool`) with `providers.stream_chat`, and flushes text into the row; every write advances `version` and the API forwards it as SSE or waits for the finished row. It is not a Cut Assistance turn: no session, tools, skills or prompts of ours. Access needs `CHAT_API_KEY` (Bearer, passed through `compose.yml`); unset means 503 because the rest of the API has no authentication. 503 also when `chat_gateway_state.heartbeat` is stale (worker down). A client disconnect cancels the row; an interrupted running row is failed, never restarted (a stream already sent part of it). Vite proxies `/v1` in development. Restart the inference worker after changing either file.
- `backend/app/single_cut_pipeline.py` runs visual analysis stage by stage across every cut in a job, following how a cut is reproduced (still image, audio, then motion): `initial_frame` (one `llama-server`, the still) and then `keyframe_analysis` (one vision-model `llama-server`, Qwen3.6 by default, and one DWPose load for every cut, `keyframe_analysis.stage`). `CutRun` holds each cut's checkpoint; `CutRun.save(..., after=)` runs a hook in the transaction that saves the result. The per-cut buttons queue a one-cut job. `POST /api/episodes/{id}/visual-analysis` queues one job for enabled cuts. Identical requests reuse the active job. Visual jobs wait for applicable media and detection prerequisites, then use `analysis_context.visual` to read cut evidence under a SQLite snapshot. The payload carries only request choices and cut IDs for new runs. Each cut's publication uses `JobInputs.publish` and records the fingerprint and source revision IDs. A changed input restarts the job after a quiet period, with unaffected cut checkpoints retained. Keep new stages model-major and checkpoint per cut so retries resume. **The video stage was replaced by keyframes on 2026-11-18** (Qwen3-VL-8B over the clip reached hand-label F1 31 against 61 for keyframes, `multiframe_experiment/PIPELINE_HANDOFF.md`): `ALL_STAGES`/`main.VISUAL_STAGES` are `initial_frame`, `keyframe_analysis`; `POST /api/cuts/{id}/analysis-stages/run {stage: 'video_analysis'}` answers 410; a `video_analysis` or `last_frame` named by an older queued job is ignored. `video_model.py` stays only for `analysis_experiments/` and to document how stored video results were made; the `video_analysis` role and the LFM3 video backend are gone. **The last frame is no longer analyzed** (removed 2026-11-12). Stored `video_analysis` and `last_frame` results stay readable everywhere (result list, history, `/api/v1`, includes, assistant `get_result`) and a cut analysed before keyframes keeps using its video analysis (see the readers below); `visual_contracts.full_last_frame` still expands old last frames.
  - First frame: the prompt lives in `visual_contracts.py` (`FRAME_INSTRUCTION`, `frame_schema`, `resolve_frame`) and is sent by `frame_model.describe_frame` as a fixed system message plus a per-frame user message, with a `json_schema` response format (a grammar; a server that rejects it gets plain `json_object`). Results are `mode: "full"` (and, since 2026-11-16, `contract: "frame-v2"`) with keys `composition`, `setting`, `lighting`, `camera`, `mood`, `visible_characters`, `background_people`, `props`, `notes`; each character has `appearance`, `position`, `pose`, `expression`, `emotion`, `gaze`, `action` (`PERSON_TEXT`). Results from before 2026-11-12 lack `mood`, `props`, `emotion`, `gaze`; older ones keep `other_visual_details`/`uncertainties`. Identity is never in doubt at this point: only boxes with a character (`marked_people` in `single_cut_pipeline.py`) are sent as short handles `B1…` with a 0-1000 box, and `resolve_frame` swaps the handles for `character` and `character_context_id` (no box ID and no identity text is stored; `composition_brief.subjects` links a character to its box by `character_context_id`, and still honors `identity_evidence` ids in older results), drops handles that were never offered and adds an entry for a marked person the model skipped. `NAME_RULE` makes the model use character names in every text field, so descriptions stay linked to characters. Unmarked people are listed in `background_people`; cuts with `no_characters` send no boxes. No reference crops are sent. Character context notes (outfits) are not sent to the frame or video prompts, and `OUTFIT_RULE` makes the model write only visible garments and "not visible" for cropped parts, because copied series descriptions were being reported as what the frame shows. The stage describes `FRAME_PARALLEL` cuts at once (default 4, one `llama-server` slot of 8192 tokens each; `_for_each(..., parallel=)`), so per-cut scratch filenames must stay unique.
  - **Keyframes (2026-11-18, `keyframe_analysis.py`):** the stage reads the cut's current keyframe selection (`keyframes.current_selection`; frames F1…Fn at 1024 px, windows of 5 sharing one frame, `keyframe_schema.make_windows`). Queueing a visual job with this stage queues the CPU `keyframes` selection for cuts without a current one in the same transaction (`keyframes.ensure_selection`, reusing a pending job, skipped when the original is missing) and lists the selection jobs in `payload.depends_on`. The analysis waits for successful selection. A failed or cancelled selection cancels the dependent visual run. Per cut: (1) names: the Target frames run when it is current for this selection and these boundaries (`target_detections` per keyframe, one slot per person, roster lines may say "first seen in F3"), else the first-frame boxes of the job's `character_detections` anchored to F1, nobody for `no_characters`; (2) CPU: the camera per pair from pixels (`keyframe_camera`: ORB + RANSAC, subtitle band masked, then every person masked out; never asked of a model), DWPose people (`keyframe_pose`, onnxruntime `CPUExecutionProvider`, anchors first then YOLOX, tracked through the camera transform, two Target frames slots never share a track) and the rules (`keyframe_rules`, ported unchanged from the experiment: per-frame states, per-pair body changes, the walking rule, the `SEATED` gate); (3) the vision model (Qwen3.6 by default since 2026-11-18; the prompt and its F1 61 were measured on Qwen3.5-27B, so re-run `multiframe_experiment/` before trusting a change in quality), one call per window (`KEYFRAME_PARALLEL` slots of 16384 tokens) with the experiment's `observer` prompt and roster context byte for byte (`keyframe_prompts.SYSTEM`, a test pins its hash; change it only with a new experiment run and `PROMPT_VERSION`), json_schema grammar, 3 attempts with the validator's sentences (`keyframe_schema`); (4) the merge (`keyframe_rules.merge`): DWPose's measured body changes replace Qwen's for that part, Qwen keeps head, eyes, mouth, expression and what DWPose did not measure, the camera is always the pixel estimate, each change carries `source` `dwpose`|`qwen`. Without the DWPose weights the stage runs Qwen alone (`method: 'qwen'`, `settings.dwpose.missing`). Tables: `keyframe_analysis_runs` (one per cut, selection and `input_hash`; provenance, phase `prepare`→`describe`→`complete`), `_frames` (keypoints, DWPose and Qwen states), `_pairs` (camera, merged changes) and `_windows` (each Qwen answer with its attempts: **the checkpoint**, so a retried job resumes from the saved windows of an unfinished run). The result `keyframe_analysis` (contract `keyframes-v1`: `roster`, `frames[].characters[{name, character_context_id, state, pose}]`, `segments[]` per pair with `camera`, per character walking/speaking/blinking and `changes`, `other_changes`, `summary`, `cut`) is saved by `CutRun.save(after=)` in the transaction that marks the run complete and queues the initial `performance_beats` job if the cut has no beats. `GET /api/cuts/{id}/keyframe-analysis` feeds the Target frames tab (states under each frame, "Changes Fk→Fk+1" between them). DWPose is the `dwpose` helper of `visual_models` (no role), pinned in `model_manifest.json`, installed with `python3 scripts/install-model.py dwpose` and mounted at `/models/dwpose` (`DWPOSE_DIR`, `DWPOSE_THREADS`); recreate the inference worker after the first install. Restart the inference worker after changing any `keyframe_*` file.
  - **Performance beats (2026-11-18, `performance_beats.py`):** a text pipeline (`worker.TEXT_PIPELINES`, text and remote lanes, `job_kinds`) that compiles the cut's acting into timed beats. It reads its inputs when it starts (`gather`): the opening `frame_view`, `keyframe_view(level='beats')`, the merged transcript lines as `S1…` with clip times, speaker, whether the speaker is in the picture near the line, whether their mouth moves at the keyframes and the app's `suggested` delivery (**never the words**), the roster names, `series_context`, and the anchors (keyframe times and line edges) every beat edge must sit on. The answer (json_schema with name and line enums, never empty) is checked by `validate` (tiles 0…duration, edges on anchors, one delivery per line; its sentences go back to the model) and saved as `performance_beats` (contract `beats-v1`: `beats[{start, end, camera, intent, characters[{character, body, face, gaze, mouth}], speech}]`, `speech[{line, speaker, start, end, delivery, suggested}]`, `checks`, `based_on: {keyframe_analysis, initial_frame}`). Deliveries are `on_screen` (lip-synced), `off_screen`, `inner_voice`, `narrative`. A keyframe result saved meanwhile makes the job finish as "Superseded" without saving. Queued by the keyframe commit when there are no beats yet (`ensure_queued`), `POST /api/cuts/{id}/performance-beats`, and the text chain. A manual or assistant edit of the keyframes marks existing beats stale; retry re-runs it. `prompt_context.beats_current` says whether the beats were built from the current keyframes. The Results tab shows them above the Review (`PerformanceBeats.tsx`). Restart the inference worker after changing it.
  - **Readers and readiness.** `prompt_context.motion_source(by_type)` is a cut's motion: its keyframe analysis presented as a motion direction (`keyframe_view.direction_from_keyframes`: summary from current beats, camera moves joined with " → ", per-character activity, travel, motion, speaking, emotion, gaze and end, clip-relative events with a kind), else a stored video analysis. `with_motion` hands it to the readers written for the video analysis as `video_analysis` (`sequence_evidence.load`, `composition_brief`, assistant sequence `get_cut_evidence`), `current_motion` reads it with SQL (`sequence_store.event_starts`), and `/api/v1/cuts/{id}` returns it as `motion` with `motion_source`, `keyframes` and `performance_beats`. Readiness (`summary_queue.missing_evidence`, `composition_brief`, the cut flag `has_visual_results`): the first frame plus, for a cut with keyframes, beats built from its current keyframe analysis; a cut **without** any keyframe analysis falls back to its video analysis (older ones still need their last frame); a cut with keyframes never falls back. Readers tell the video generations apart with `prompt_context.is_direction(content)`. `prompt_context.frame_view`/`keyframe_view`/`beats_view`/`video_view` are the compact forms text prompts get; `slim_results` applies them and drops an older `Video analysis` and a leftover `Last frame description` once the cut has keyframes (the last frame also once it has a motion direction). `consistency_summary.build_input` sends `First frame` + `Keyframes` + `Performance beats` for keyframed cuts, `First frame` + `Video analysis` for motion directions and the three older blocks otherwise; `app_checks` adds `delivery_against_mouth` and `beats_stale`. The text chain queues the beats first when they are missing or stale (or reuses the waiting job) and the consistency job waits for it (`depends_on`, `refresh_evidence`: `consistency_summary.refresh` rebuilds the evidence from the stored `refresh` inputs when it starts); The worker applies the same dependency rules to the text chain and every other pipeline. A Cut summary queued while beats are being written waits for them and reloads the results (`refresh_results`). The reviewer, answers and Cut summary prompts: the first frame decides the start, the keyframes decide change over time (the video analysis for older cuts), the beats are the timed acting plan and decide each line's delivery, and where a beat contradicts the keyframes the keyframes win. **The Cut summary is a performance director's brief since 2026-11-18** (`production_brief_prompt.txt`): five sections Scene, Opening Frame, Performance Beats (`[start–end] Name: body; face; gaze; mouth (delivery). Intent: …`), Acting Notes, Continuity & Constraints (`inference_worker.BRIEF_SECTIONS`, at most `BRIEF_MAX_BYTES` = 7168 since 2026-11-19, 6144 before); the validator still accepts the four sections of 2026-11-16 (`PREVIOUS_BRIEF_SECTIONS`) and the older five with Dialogue so editing an old summary saves; the third section is always the timed one. **Cinematic Camera (2026-11-19):** a sixth, last section that says which real camera and look would have made the opening frame as a live-action cinematic shot, for the still generator: seven bullet fields `Camera body`, `Lens`, `Focal length`, `Aperture`, `Lighting`, `Color grading`, `Image texture` (`CAMERA_SECTION`, `CAMERA_FIELDS`, `CAMERA_BRIEF_SECTIONS`; prompt section 12). The prompt prefers the ARRI Alexa family (the user's choice: it gives good stills) and picks the model from the frame, and never names an animation style. A model answer must have it (`validate_production_brief(camera=True)`, applied when the instructions sent contain the section name, so an edited request is not forced; its sentences go back to the model: a missing field, or one that says unknown/n/a); older layouts still validate without it, so editing an old summary saves. The byte cap is now 7168 (`BRIEF_MAX_BYTES`) so the five other sections keep their room. `brief_picture.py` sends the cut's first frame (`assistant.images.picture(cut_id, 'first')`) after the evidence when `endpoint_vision(provider)` is true and the request leaves room in one slot, and appends `PICTURE_NOTE` to the instructions: the picture is **only** for this section, every other section still follows the text evidence. No picture goes with a request override, with OpenRouter or a text-only server; a frame that cannot be cut never fails the job. The result's `settings` record `picture: 'first frame'` or `picture_skipped: <why>` (and `usage.pictures`), and `prompt` is the instructions as sent. Sequence code was not changed: the section can reach shot prompts through `cut_summary` in `sequence_evidence` (strip it in `without_dialogue` if gear names should stay out of them), and `assistant/skills/still_image_prompt.md` still names only the Opening Frame section as its source. Restart the inference worker after changing the prompt or `brief_picture.py`. It is written from the analysis and the user's answers only: `process_regen` leaves the transcript, subtitles and the Consistency summary out of its request, and it holds no dialogue text or speaker turns (the sequence's Dialogue step owns those; a beat's mouth action and delivery label are allowed). Subtitles are not a cut stage: jobs only receive the episode's subtitle language and strip (`context.subtitles`) so the visual prompts can ignore it. Older `subtitle_ocr` results stay readable as history and as a composition-brief fallback until the episode is extracted.

## Invariants and extension points

- The original video must never be overwritten by proxy or inference work.
- Database IDs are UUIDs; construct media paths only from database rows and fixed filenames.
- Long-running media work belongs in the queue, not an HTTP request.
- Keep `uvicorn --workers 1` for the current deployment. The media worker runs in the API process; separate inference and audio workers claim only their own pipeline kinds through SQLite and use the same lease discipline.
- A failed job records its error; reruns are allowed. Existing cut edits and result IDs are retained when redetection finds the same boundary within 0.25 seconds. Unmatched cuts become inactive archives rather than being deleted; later matching boundaries reactivate their IDs. Do not delete and reinsert cut rows: foreign keys would cascade-delete result history. The one exception is `cut_history`: undoing a split removes the cut the split created, but only if it has no notes and no row refers to it (every table with a foreign key to `cuts` except the `composition_changes` watermark, plus `sequences`). Otherwise the cut is archived. The `cuts` table keeps negative `cut_index` values for archives and nonnegative indices for active timeline cuts.
- Media and model cache volumes must survive image rebuilds.
- Keep ROCm/CUDA inference in separate optional worker images with pinned compatible PyTorch/runtime packages. Store model provenance and prompt/settings with each result. Do not put generated text into files that replace originals.
- Read `docs/model-integration.md` before changing the WeVisOne-VL adapter. Its documented tasks are frame-level perception, and container ROCm compatibility still needs validation. Do not download weights before a task explicitly calls for model inference.
