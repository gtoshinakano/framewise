# Agent guide

Framewise is a local-first video analysis app. Preserve the hierarchy `Project → Episodes → Original Video` and the original upload. Sequences are an optional layer above cuts: a range of cuts directed as one short video (see the code map). The working flow is import → background media preparation → user-triggered hard-cut detection → timeline playback and editable cut notes, with optional queued visual analysis (first frame, then video motion), audio transcription, and an episode-wide burned-in subtitle extraction that the user runs after transcription. Do not download models without a task requiring them.

## Code map

- `backend/app/main.py`: FastAPI endpoints and input validation.
- `backend/app/db.py`: SQLite schema and connections. Database and media persist under `DATA_DIR` (`/data` in Docker).
- `context_items` stores project or episode scoped chapter, character, world, scenario, object, and general notes for inference prompts.
- `analysis_results` stores per-cut text with revision links and optional model/job provenance; `transcript_segments` stores timed audio text and speaker/character links with revisions. Default reads return current results and current non-deleted transcript segments; `?history=true` returns the full revision chain. All current results and overlapping non-deleted transcript segments are usable for analysis. Results and transcripts have no approval status; do not add one to the database, API, prompts, or UI. `/api/cuts/{id}/analysis-context` supplies adjacent cuts and their current results, applicable context items, chunks, transcript overlap, and the `subtitles` object (`extracted`, the episode's subtitle `language`, the `strip`, and the subtitle `lines` overlapping the cut with `crosses_cut`). Transcript deletion revisions retain a separate `deleted` flag.
- `backend/app/worker.py`: one background media worker claims jobs from SQLite. Claims use a 60-second renewable lease, three-attempt interruption limit, and queued settings snapshot. Queued and interrupted jobs survive process restarts.
- `chunks` stores timed working segments for long videos; cuts are independent visual boundaries and may cross chunk edges.
- `backend/app/prompt_context.py` slims what text prompts (consistency summary, review answers, Cut summary) receive: transcript lines are only start/end, text, `speaker_label`, `character_name` (current, non-deleted); neighbouring cuts contribute only their Consistency summary; first-frame and motion-direction results are sent as compact objects (`frame_view`, `video_view`); detections drop recognition scores, `match_reason`, model names and ids; results drop ids, kinds and model names. Route any new prompt input through it instead of sending rows. The API and `/api/v1` keep the full context.
- `backend/app/inference_worker.py` runs `TEXT_JOB_CONCURRENCY` (default 2) local text jobs at once: the main loop plus `text_lane` threads that claim only `regen`, `consistency_summary` and `review_answers` (`worker.TEXT_PIPELINES`, which `claim_job` lets share an episode), each holding a `chat_session` so visual jobs release the GPU only after they finish, and the Qwen3.6 server runs with that many `--parallel` slots (`QWEN36_CONTEXT_SIZE` is split between them, 32768 each by default). Restart the inference worker after changing either setting. The text server has two interchangeable model files chosen by `text_generation_settings.local_model` (`standard` Q4_K_M, or `mtp`, the Unsloth UD-Q4_K_M with the multi-token-prediction head that `llama-server` uses for `--spec-type draft-mtp`; `local_text_runtime.VARIANTS`, `QWEN36_MTP_MODEL_PATH`, `QWEN36_MTP_ARGS`, `scripts/download-qwen36-mtp.sh`). The worker publishes `local_text_model_state.variant` and `variants_json` (installed/downloading), `PUT /api/text-generation-settings` refuses an uninstalled variant, and `LocalTextRuntime` switches only when `can_switch()` (no request in flight via `runtime.request()`, no other chat session); text lanes claim nothing while `switch_pending()`. `chat_json` re-asks `runtime.request()` for the server address on every attempt and saves `model_variant`, `predicted_n/ms`, `decode_tokens_per_second` and `draft_acceptance` in each result's `usage`; `GET /api/text-model-comparison` averages them and the text engine dialog shows the table. Never hardcode the model revision: use `local_text_runtime.revision_for(usage['model_variant'])`. It also claims visual `analyze`, `regen` and `subtitles` jobs. `POST /api/cuts/{id}/regenerate-summary` queues a revision of the `Cut summary` result and fails if that result changed while queued; the worker also supports older queued animation-prompt jobs. Analyzed frames are saved as `analysis/{result_id}.jpg` beside the original so `/api/analysis-results/{id}/frame` can serve them under detection overlays. `SUBTITLE_RULE` prevents treating subtitles as objects to reproduce. The UI lives in `AnalysisDialog.tsx`, `DetectionPreview.tsx`, `ResultEditor.tsx`, and `AnimationPromptPanel.tsx`.
- `backend/app/single_cut_pipeline.py` runs visual analysis stage by stage across every cut in a job, following how a cut is reproduced (still image, audio, then video): `initial_frame` (one `llama-server`, the still) and then `video_analysis` (one `video_model.VideoRuntime`, the motion). `CutRun` holds each cut's checkpoint. The per-cut buttons queue a one-cut job; `POST /api/episodes/{id}/visual-analysis` queues one job for all enabled cuts. Keep new stages model-major and checkpoint per cut so retries resume. **The last frame is no longer analyzed** (removed 2026-11-12: it cost about 16 s per cut and mostly answered "unchanged"). Do not add it back as a stage: `ALL_STAGES`/`main.VISUAL_STAGES` are `initial_frame`, `video_analysis`, and a `last_frame` named by an older queued job is ignored. Stored `last_frame` results (`mode: "changes"` or full) stay readable everywhere (result list, history, `/api/v1`, `include=last_frame`, assistant `get_result`) and `visual_contracts.full_last_frame` still expands them for cuts whose video analysis predates motion directions.
  - First frame: the prompt lives in `visual_contracts.py` (`FRAME_INSTRUCTION`, `frame_schema`, `resolve_frame`) and is sent by `frame_model.describe_frame` as a fixed system message plus a per-frame user message, with a `json_schema` response format (a grammar; a server that rejects it gets plain `json_object`). Results are `mode: "full"` with keys `composition`, `setting`, `lighting`, `camera`, `mood`, `visible_characters`, `background_people`, `props`, `notes`; each character has `appearance`, `position`, `pose`, `expression`, `emotion`, `gaze`, `action` (`PERSON_TEXT`). Results from before 2026-11-12 lack `mood`, `props`, `emotion`, `gaze`; older ones keep `other_visual_details`/`uncertainties`. Identity is never in doubt at this point: only boxes with a character (`marked_people` in `single_cut_pipeline.py`) are sent as short handles `B1…` with a 0-1000 box, and `resolve_frame` swaps the handles for `character` and `character_context_id` (no box ID and no identity text is stored; `composition_brief.subjects` links a character to its box by `character_context_id`, and still honors `identity_evidence` ids in older results), drops handles that were never offered and adds an entry for a marked person the model skipped. `NAME_RULE` makes the model use character names in every text field, so descriptions stay linked to characters. Unmarked people are listed in `background_people`; cuts with `no_characters` send no boxes. No reference crops are sent. Character context notes (outfits) are not sent to the frame or video prompts, and `OUTFIT_RULE` makes the model write only visible garments and "not visible" for cropped parts, because copied series descriptions were being reported as what the frame shows. The stage describes `FRAME_PARALLEL` cuts at once (default 4, one `llama-server` slot of 8192 tokens each; `_for_each(..., parallel=)`), so per-cut scratch filenames must stay unique.
  - Video: `VIDEO_INSTRUCTION` asks for a motion direction, not a description (`contract: "direction-v2"`): per window `overview`, `camera` (`movement` from `CAMERA_MOVES`, `detail`), `characters` (`activity`, `travel`, `motion`, `speaking` yes/no/unclear, `emotion`, `end`), timed `events` and `uncertainties`. `single_cut_pipeline._video_analysis` builds `visual_contracts.video_roster` from marked first-frame characters and the first-frame result this job (or an earlier one for the same cut boundaries) saved, and `video_model.analyze_video` adds it to each window's prompt (`roster_note`), together with who speaks when without the words (`speech_note`, from the transcript snapshot), what the previous window reported (`earlier_note`) and non-character series notes (`series_note`). `link_video` turns model-written names into `character`/`character_context_id` (exact, or the only roster name containing all its words) and `cut_direction` merges the windows into `direction` (`summary`, `camera`, `characters`, and optional historical `end_state.in_frame`/`in_last_frame` presence confirmation). Current runs use first-frame boxes only; the video model reports each character's end state. Historical directions may keep their saved last-frame confirmations. `main.automatic_video_fps` samples a cut of up to 6 s as 30 frames so it is one window (events are not split, about half the video tokens); longer cuts keep 56 frames in windows of at most 32. Saved windows carry `source.contract` and are only reused by a retry under the same contract.
  - Readers tell the two generations apart with `prompt_context.is_direction(video content)`. `prompt_context.frame_view`/`video_view` are the compact forms text prompts get (one clip-relative event list, no window bookkeeping); `slim_results` applies them and drops a leftover `Last frame description` once the cut has a motion direction. `summary_queue.payload_for` needs only the first frame and the video analysis (an older video analysis still needs its last frame), `consistency_summary.build_input` sends `First frame` + `Video analysis` for motion directions and the three older blocks otherwise, and `composition_brief` is ready without a last frame, adds `mood`, `props`, `action`, subject `emotion`/`gaze`/`motion` and marks a subject `left frame` from its video end state and honors historical `in_last_frame` evidence when present. The reviewer, answers and Cut summary prompts are written around the three generation steps (still, audio, motion): the first frame decides the start, the video analysis decides change over time, historical `end_of_cut.in_frame` confirms presence when present, while current end states come from motion analysis, wording differences between the two models are not review items, and `speaking` decides whether a transcript line is lip-synced, an inner voice or off screen. The Cut summary keeps its five headings (validated in `inference_worker.validate_production_brief`, at most `BRIEF_MAX_BYTES` = 4096). Subtitles are not a cut stage: jobs only receive the episode's subtitle language and strip (`context.subtitles`) so the visual prompts (`visual_contracts.subtitle_note`) can ignore it. Older `subtitle_ocr` results stay readable as history and as a composition-brief fallback until the episode is extracted.
- Subtitle extraction is one independent episode-wide `subtitles` job (button in the audio tab, `SubtitlePanel.tsx`; `POST /api/episodes/{id}/subtitles {language}`, read with `GET`). The user must state the single subtitle language; it is validated by `subtitle_reader.resolve_language`, saved in `episodes.subtitle_language`, stored on the run, and given to the model as a certain fact, then each reading is checked against that language's script. `subtitle_pipeline.py` runs in the inference worker: WeVisOne locates the strip on probe frames chosen from transcript speech (`subtitle_scan.choose_probe_times`/`band_from_probes`) and measures whether the style is outlined; `subtitle_scan.py` decodes only that strip once on the CPU (`scan_video`: bright thin strokes that persist between frames, static overlays removed, optional dark-outline test, events when the stroke mask changes); the Qwen3.5 `llama-server` (`SUBTITLE_READ_PARALLEL` slots) reads one strip image per event (`subtitle_reader.py`). Rows live in `subtitle_runs` (language, strip, diagnostics, prompt), `subtitle_readings` (one per scan event, the checkpoint) and `subtitle_lines` (merged, time-ranged, not tied to any cut); the latest `complete` run is current and older runs stay as history. A failed or interrupted run is reused by the next run for the same language and prompt, so only unread events are read again. Cut analysis reads lines by overlap through `subtitle_store.cut_context`, which feeds the consistency summary, Cut summary, review answers, composition brief, assistant `get_subtitles` and `/api/v1`. Do not add a per-cut subtitle stage or an approval status to subtitle lines.
- `backend/app/review_answers.py` backs the `review_answers` inference job (button in the answers textarea of `CutSummaryPanel`): it drafts short topic answers to the Consistency Summary's Human review and Suggested checks from the cut's results, neighbouring `Cut summary` results (falling back to their video analysis and transcript), and the current answers. The draft is stored in `cut_review_drafts` and only fills the textarea unsaved; it is never an analysis result and has no approval status. The single-cut button only fills the textarea; `POST /api/episodes/{id}/review-answers?from_cut=N` (Run settings: "Queue production decisions draft from this cut") queues the same job with `payload.auto_save` for this and every later cut that is ready (consistency summary present, something to decide or saved answers, no analysis/consistency/answers job pending; the rest come back in `blocked`), and the worker then saves the draft as the cut's answers only while they still equal `payload.existing_answers` (the replaced text stays in the job payload). `POST /api/episodes/{id}/cut-summaries?from_cut=N&only_missing=true` ("Queue Cut Summary from this cut") queues `regen` jobs for ready cuts that have a consistency summary and no Cut summary, and holds back cuts whose answers job is still pending because a summary snapshots the saved answers when queued. `POST /api/episodes/{id}/text-chain?from_cut=N&only_missing=true` ("Queue all three text steps" row in Run settings) queues consistency summary, answers (`auto_save`) and Cut summary for every ready cut as one chain per cut: each job's `payload.wait_for` names the job before it, `worker.claim_job` holds a `regen`/`review_answers` job until that one is `done` and fails it (cascading) when it failed, was cancelled or is gone, and the waiting job re-reads what the chain wrote when it starts (`review_answers.refresh` replaces the consistency summary and saved answers, and finishes as `Nothing to decide` without calling the model if nothing is left to decide; `regen` with `refresh_answers` reloads the saved answers and, through `depends_on_consistency`, the new consistency summary). With `only_missing=false` every ready cut gets a new Cut summary, and a cut whose chain is still pending without that step gets it added behind its answers job (`attached` in the response). Never snapshot a chained job's inputs at queue time. Restart the inference worker after changing either.
- Bulk character detection (`anime_bulk.py`) runs in phases stored in `character_detection_runs.phase` (`boxes` → `embeddings` → `complete`) with per-step `timings_json` (also logged as `character-detect … took Ns` by `framewise.character_detect`). `POST /api/episodes/{id}/character-boxes` (UI: Detect Character Boxes) runs AniRef on the first frame; `POST /api/episodes/{id}/character-detection` (UI: Detect Missing Characters) matches boxes with the gallery; `POST /api/episodes/{id}/character-detection-all` (UI: Detect All Characters) does both in one pass (`phase='full'`); `POST /api/episodes/{id}/character-detection-rerun` (UI: Re-run Recognition) clears automatic labels and redoes recognition in every cut, never touching manual labels or drawn boxes and skipping cuts whose boxes are all manual. Batches of 16 cuts extract frames in parallel, then run AniRef, then the embedder, model-major (`anime_bulk.process_batch`). Recognition compares each box with the gallery (`anime_gallery.py`): every manual label in each cut's latest run plus saved references, embedded with CCIP by default (`anime_models.create_embedder`, `ANIME_REID_BACKEND=ccip|dinov3`; weights from `scripts/download-ccip.sh`), scored as the mean of each character's top-3 similarities, with per-embedder thresholds in `anime_models.*_DEFAULTS`. Never add automatic labels or tracks to the gallery. Confirmed boxes that cannot identify anyone (too small, or more like another character) keep their label but are left out of matching (`gallery_status`, `gallery_note`; user override `recognition_use`, `PUT /api/character-detections/{id}/recognition-use`). Unconfirmed boxes store their top-3 `candidates_json`, shown as one-click suggestions in `CharacterDetectionPanel.tsx`. There is no vision-model step: a box the gallery cannot settle keeps its shortlist and the user picks one on screen (Ask Qwen was removed on 2026-11-10 because it took about 93% of detection time). Cuts with `cuts.no_characters=1` (`PUT /api/cuts/{id}/no-characters`) are skipped. The first frames are cached in `character-frames/` beside the original and removed per cut when it reaches `complete`. The cut panel's Detect characters button (`POST /api/cuts/{id}/character-detection`) queues the same workflow for one cut with Re-run semantics, ignoring that cut's `no_characters` and analysis switch; `process_character_detection` (WeVisOne + pairwise Qwen) only serves jobs queued before that change. Restart the inference worker after changing these files.
- `backend/app/assistant/` backs the "Assistant" tab, called Cut Assistance in the chat (`CutAssistant.tsx`, `assistantApi.ts`, `assistantFormat.ts`, `Markdown.tsx`). `api.py` stores sessions (`assistant_sessions`), messages and queued turns; `runner.py` runs turns on a thread in the inference worker (`start_assistant`) with the shared lease discipline, streams provider deltas into `assistant_messages`, and advances `assistant_turns.version` so `GET /api/assistant/turns/{id}/stream` (SSE) forwards them. `LocalTextRuntime.chat_session` keeps llama-server alive during a chat turn and `begin_gpu_work` blocks chat loads during visual work. A turn with `assistant_turns.gpu_fallback` (the "OpenRouter if GPU busy" checkbox) opens the local session with `wait=False`; `runner.connect` catches `GpuBusy` and answers that turn with `providers.FALLBACK_MODEL` (`openrouter/free`) instead of waiting, recording `usage.fallback` and keeping `turn.provider/model` as the user's local choice. Only `local` turns fall back, and only when the worker's OpenRouter key is set. Tools are registered with `@tool` in `tools.py` and return compact, clip-relative JSON (keep payloads small and add `fields`-style narrowing for new large tools); skills are `skills/*.md` with front matter, loaded on demand via `load_skill`. Result changes are only `assistant_proposals` until the user applies them, which appends an `assistant_edit` revision and refuses stale bases. `propose_transcript_edit` (`transcript_edit.py`) is the same for the audio transcript: it works on the numbered speaker lines of `get_transcript` (`merged_transcript` merges word fragments, `ids` maps a line back to them), stores a fragment-level plan in `assistant_proposals.payload_json` with readable before/after text for the card diff, and applying writes `assistant_edit` revisions/tombstones of `transcript_segments` (no result row; stale when any replaced segment was revised or its character deleted). One call per turn: a later one replaces the earlier unsaved transcript proposal. Providers (`local`, `openrouter`, `ASSISTANT_ENDPOINTS`) live in `providers.py` and the worker publishes availability to `assistant_worker_state`. H3 prompts follow the external AI director's six-section FastH3 OmniRef format: `h3_prompt.py` checks it deterministically, and `check_h3_prompt` compares a draft with the prompt the user pasted (never the model's own copy). It restores the app's picture/audio lines and curly-quoted names verbatim, and rejects changed `<Picture|Audio|Video N>` numbers, record names, file names or shot length, because the other app's files are bound to them. New `<d>` speech must quote the transcript verbatim (`get_transcript` merges word-level fragments into speaker lines). Tools marked `must_pass` make the runner send the model back when it answers while their check fails.
- Sequences (`backend/app/sequence*.py`) are a layer above cuts: the user picks a contiguous range of active cuts lasting at most 180 s (`sequences`: `first_cut_id`, `last_cut_id`, a `cuts_json` snapshot) and the text model directs it as one short video on the original audio, generated shot by shot with MiniMax H3. Results live in `sequence_results` (`type` `bible`, `plan`, `shot` keyed by `shot_key`, `review`) as revision chains like `analysis_results` (`parent_id`/`superseded_by`, origins `model`, `manual_edit`, `assistant_edit`); they have no approval status, do not add one. The split of work is the point of the design: the app calculates and the model decides. `sequence_timeline.py` (pure, no database) builds the sequence clock, speech lines `L1…` from merged transcript fragments, pauses from the RMS level of `audio.wav`, and candidate boundaries `B0…` (every hard cut, plus `pause`/`event`/`quiet` points inside cuts of 8 s or more, so that a partition into shots of at most 15 s always exists); it checks a plan (`check_model_plan`, `check_spans`), completes an invalid one (`auto_fix`), and derives everything per shot in `expand` (episode times, `generate_seconds` of at least 5 with `trim_seconds` for shorter shots, the initial frame, the dialogue split by word at boundaries). `sequence_direction.py` holds the four system prompts, `json_schema` answer formats (plan boundaries are enums of the candidate ids) and validators whose error sentences go back to the model. Describe rules in those prompts instead of giving concrete example sentences: the model copied an example framing lock verbatim into unrelated shots. `sequence_prompt.py` renders a shot's direction (a JSON object the model writes with names, never labels) into the six-section H3 prompt and a still prompt: it numbers `<Subject N>`, `<Picture 1>` (initial frame), one character sheet per named subject (`MAX_SHEETS` = 4), an optional scenario picture and `<Audio 1>`, writes timecodes, the camera sentence, `<d>[Language] words</d>` copied from the transcript and the audio lines, and checks the result with `assistant.h3_prompt.check`. `sequence_evidence.py` builds each call's input when the job starts (cut digests, how the opening frames describe each character, per-shot evidence on the shot's clock with the neighbouring shots' end and opening states because shots are written in parallel, and a voice-evidence table that leaves lines without a diarization label undecided) and `fit` lowers the detail level until it fits one server slot (`QWEN36_CONTEXT_SIZE / TEXT_JOB_CONCURRENCY`); `shot_hashes` fingerprints the plan entry, the bible parts and the cuts' results so `sequence_view` can report a shot as `stale` and why. Jobs are pipeline `sequence` with `payload.step` (`bible`, `plan`, `shot`, `review`), claimed by the main loop and the text lanes (`worker.TEXT_PIPELINES`), processed by `sequence_pipeline.py`: `direct` queues the bible, which queues the plan in its commit transaction, and then the flow stops for the user; `shots` queues one job per shot that is missing, stale or failing its check (two run side by side) and the last one of a whole batch queues the review. Never snapshot a sequence job's inputs at queue time, and keep follow-up jobs in the same transaction as the result that enables them. `payload.base_id` is the revision the job was queued against, so a hand edit made meanwhile is not overwritten. A changed cut range (`cuts_changed`) blocks shot jobs until the sequence is directed again. `sequence_edit.py` queues steps and validates hand or assistant revisions exactly like model answers (`revise`, `reshape` for merge/split, `preview_shot`); `sequences.py` is the HTTP API (`/api/episodes/{id}/sequences`, `/api/sequences/{id}`, `/run`, `/cancel`, `/plan/merge`, `/plan/split`, `PUT /api/sequence-results/{id}`). `sequence_view.package` is the download contract `sequence-v1`, served by `/api/v1/sequences/{id}` and exported as a ZIP by `sequence_export.py` through the existing `brief_export` pipeline (`payload.kind == 'sequence'`, same status and download endpoints). A sequence chat is an `assistant_sessions` row with `sequence_id` (its `cut_id` is the sequence's first cut); tools carry a `scope` (`cut`, `sequence`, `any`), the sequence tools are in `assistant/sequence_tools.py` (`get_sequence`, `get_shot`, `get_cut_evidence`, `get_sequence_transcript`, `propose_shot_edit`, `propose_plan_edit`, `propose_bible_edit`), skills have a `scope` in their front matter, and proposals with target `sequence_shot`/`sequence_plan`/`sequence_bible` apply through `sequence_edit.revise`. The UI is the Sequences inspector tab (`SequencePanel.tsx`), the Sequences timeline lane and the workspace `SequenceDialog.tsx` (Direction, Shots, Assistant); `sequenceView.ts` holds its pure helpers. Sequence jobs are excluded from the `composition_job_*` watermark triggers. Restart the inference worker after changing any `sequence_*` file or `assistant/sequence_tools.py`.
- `backend/app/cut_timeline.py` backs `GET /api/cuts/{id}/timeline` and the "Analysis timeline" bar (`AnalysisTimeline.tsx`) under the Analysis dialog header. Events come from jobs, `analysis_job_stages`, `character_detection_runs`, `cut_brief_instructions`, and `cuts.created_at` (null for cuts created before it existed). Durations count execution only (start to finish, never queue time); undated legacy events show with 0s. Each kind has its own colour; unfinished kinds appear as pending.
- The Results tab of the Analysis dialog (`AnalysisDialog.tsx`) is a video/audio rail plus a three-step workbench: Review (`ConsistencySummary.tsx`; `consistencyView.ts` only reshapes the stored JSON for reading, ordering Human review and Suggested checks first and splitting them into numbered items), Your answers and Cut summary (`CutSummaryPanel` in `AnimationPromptPanel.tsx`, one component because the summary is written from the saved answers). Panels use `StepPanel` from `ReviewUi.tsx` and take their colours from `AnalysisTimeline`'s `KINDS`. From 1536px they are three columns that scroll on their own; below that Review sits beside the answers and summary stacked. The Cut summary opens in a formatted Read view (`.md-summary`) with the raw Edit view one click away. `ResultEditor` is the last item of the Review column (one icon row per result, icon by content type) and portals its field editor into `.editor-overlay`, a grid child that covers the answers and summary columns so the list stays visible. Panel status chips are `tag`s floating on the panel's top edge, so the workbench keeps 12px of top padding for them. The rail holds only the video and `CutAudioPreview`, whose spoken words take the remaining height; analyzed frames are two icons in the video corner (`FrameTools`) that open `FramesDialog` or download a frame (both in `DetectionPreview.tsx`). `CutAudioPreview` follows the video's time itself so playback does not re-render the tab. Frontend only: results and subtitle lines have no approval status here either.
- `backend/app/audio_worker.py` handles separate transcription and voice-sample jobs. The inference and audio workers use the shared SQLite lease discipline. A `transcribe` job whose payload has `range` (`POST /api/episodes/{id}/transcribe-range`, UI: `TranscribeRangePanel.tsx` in the audio tab, Shift-drag on the timeline waveform) redoes only that interval via `transcribe_range`: it diarizes the interval plus `CONTEXT_SECONDS` around it, `audio_matching.reconcile_speakers` renames the excerpt's local speakers after the labels the neighbouring speech already uses (then the label of their voice-matched character, else a fresh `SPEAKER_NN`), and one transaction tombstones the untouched model segments whose midpoint is inside (hand-edited ones are kept unless `replace_manual`) and appends the new ones. Everything outside the interval and all earlier revisions stay. The range is a payload field, not a new pipeline name, so restart the audio worker after changing it or an old worker would claim a range job and redo the whole episode.
- `backend/app/external_api.py` defines read-only `/api/v1` integration endpoints and response schemas. `/docs` serves locally bundled Swagger UI, `/openapi.json` is generated from the FastAPI models, and `backend/app/integration-guide.md` supplies both the Swagger description and `/api/integration-guide`. Keep the guide and schemas aligned with endpoint behavior; the reusable retrieval-skill prompt is in `docs/agent-skill-prompt.md`.
- `backend/app/media.py`: FFprobe/FFmpeg preparation, waveform, scene detection, and per-cut first/last frames. Frame URLs use cut IDs so redetection can retain existing cut records.
- `frontend/src/App.tsx`: React project manager and episode editor. `Timeline.tsx` windows long recordings and clips its lanes to the visible range; `CutGallery.tsx` pages cut cards.
- The episode editor polls `/api/episodes/{id}/status` for job changes and only loads the full episode every 30 seconds while idle. Keep the waveform cache keyed to the latest completed Prepare job when changing this flow.
- `compose.yml`: persistent data and model cache; optional GPU overrides are separate.
- `deploy/framewise.service`: optional systemd unit for Cockpit Services start/stop. Update its `WorkingDirectory` if the checkout path changes.

## Invariants and extension points

- The original video must never be overwritten by proxy or inference work.
- Database IDs are UUIDs; construct media paths only from database rows and fixed filenames.
- Long-running media work belongs in the queue, not an HTTP request.
- Keep `uvicorn --workers 1` for the current deployment. The media worker runs in the API process; separate inference and audio workers claim only their own pipeline kinds through SQLite and use the same lease discipline.
- A failed job records its error; reruns are allowed. Existing cut edits and result IDs are retained when redetection finds the same boundary within 0.25 seconds. Unmatched cuts become inactive archives rather than being deleted; later matching boundaries reactivate their IDs. Do not delete and reinsert cut rows: foreign keys would cascade-delete result history. The `cuts` table keeps negative `cut_index` values for archives and nonnegative indices for active timeline cuts.
- Media and model cache volumes must survive image rebuilds.
- Keep ROCm/CUDA inference in separate optional worker images with pinned compatible PyTorch/runtime packages. Store model provenance and prompt/settings with each result. Do not put generated text into files that replace originals.
